本 change 只落契约，不落代码。判据基线 2026-11-10：

- 生产者侧已实现：fork 仓 `feat/ciyuan-capabilities` 分支（worktree `/Users/chengsishi/sub2api-cap-wt`），
  `internal/lanes/capabilities.go` 400 行 + `handler/lanes_capability_models.go`；15/19 任务勾；
  `build` / `lanes` / `routes` / `vet` 全绿；**未出片、未上产**。
- 消费侧现状：壹座探针式 sync 在产（`server/routes/llm.js:182`），各线 `llm.py` 硬编码默认模型。
- 既有 `ciyuan-*` 契约五条全部是「实现归属 fork 仓 + 跨仓审计」形态，本条沿用。

## Goals / Non-Goals

**Goals**

- 让六条线的接入方对同一份 JSON 得出同一结论（尤其是「什么不能推」）。
- 让降级成为契约义务，而不是各线自觉——否则接入一次事故就把端点拖成故障源。

**Non-Goals**

- 不复制生产者侧的响应字段表与推导实现（那在 fork spec；复制即漂移源）。
- 不规定消费方的 UI 形态。
- 不在本 change 做任何接入代码。

## Decisions

**D1 契约只写「消费方可依赖 / 禁止推断 / 降级义务」三件事，不重复生产者字段表。**
备选「把 fork spec 整段复制到 paas」（既有五条契约的实际做法）被否：本仓已有多次同一事实写两面
各自漂移的实证（谱系台账与配对 spec 都出现过）。本条改为**引用 + 语义约束**，审计判据从
「字段是否逐个相同」变成「两文件对同一字段的表述是否可同时为真」——这个判据可以自动化成一条 grep/断言，
也允许两侧措辞不同。

**D2 `null` / `false` / `0` 的三分法写进契约，而不是留给消费方猜。**
词元在生产里已多次栽在「读不到当成不存在」（credentials 静默清列、记忆链断链同族），
若契约层不锁死这条，六条线会各自把这三种值当一回事。

**D3 降级义务列成硬要求，并强制保留探测为校验。**
理由：能力快照是**新增的便利**，不是移除既有路径的前提。若某线按「快照在就不探测」清理，
一旦词元滚版或端点 503，该线会静默失去模型识别能力——比现状更差。

**D4 不规定「推荐默认模型」字段。**
fork 实现里有意未做（需产品决策：按线推荐 vs 按 key 权益推荐）。契约若先写形状，会逼生产者
按一个未裁定的语义实现；故 `serving[]` 只承诺「大概率可服务」，选哪个由消费方自决。

## Risks / Trade-offs

- **[契约写得太软，消费方仍各解各的]** → 禁止推断清单是封闭枚举（五条）+ 违约即视为契约违约，
  比抽象原则更容易在评审时引用。
- **[双仓一致性靠人]** → D1 的判据（「可同时为真」）可落成一条审计脚本；
  但本 change 不实现脚本，只登记为后续（见 tasks 3.1）。
- **[端点未上产即先写契约]** → 有意如此：消费方接入前需要先有判据，否则接入顺序会反过来
  逼生产者改语义。契约与实现可并行，验收仍以真机为准。
