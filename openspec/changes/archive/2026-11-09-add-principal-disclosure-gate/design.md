## Context

见 `proposal.md` — Why。三条现状约束决定做法：

1. **披露判定已经是纯函数**（`lib/personal-mandate.js` 的 `checkDisclosure`）：读 `contentArgs` 原文、三类依据（provenance / pattern / term）、返回可解释越界项。Lane B 缺的不是判定能力，是**判定被接在对外发言链路上**——门面应答与 IM 回复今天不经过它。
2. **台账列已经存在**（`action_audit` 的 `mandate_ref/mandate_domain/mandate_mode/disclose_level/reversible_until/content_digest/revoked_at`，migration v116）。Lane B 只补 `principal` 与 `audience` 两列，不新建表——理由与上一个 change 相同：两本账一定会对不上。
3. **单执行路径是既定合同**（`action-gate` 的「单一执行路径与审计台账」）。对外发言必须挂到这条路径上，而不是新开一条「消息发送」路径——一旦有第二条路径，披露闸就必然有旁路。

## Goals / Non-Goals

**Goals:**

- 对外发言**结构上不可能**绕过披露闸（不是「默认走闸，特殊情况下可以绕过」）。
- 每句对外的话都能回溯到：谁授权的、哪个代理说的、引用了哪条判例、能否撤回。
- 内外部两套形态共用同一份内容与同一条授权，审核只做一次。

**Non-Goals:**

- 不做语音/电话外呼；不做跨委托人代理。
- 不改披露层级的枚举（先用 `add-personal-mandate` 立的五档）。
- 不做门面语料的自动更新节奏（既有 change 的语料冻结需求仍在）。

## Decisions

### D1 · 对外发言注册成受闸动作，而不是给发送链路加钩子

在 `lib/action-registry.js` 新增对外发言动作条目（`risk: write`、`outbound: true`、`contentArgs` 指向正文），门面应答与 IM 回复都通过 `executeRegisteredAction` 发出。

- **否决 (a)**：在发送函数里加一个「先问一下披露闸」的钩子。钩子可以被新写的发送函数忘掉，而注册表**忘不掉**——`action-gate` 的「未注册动作 MUST NOT 执行」是既有硬约束。
- **理由**：把「对外发送」变成一个有 id、有风险等级、有审计的动作，是让披露校验拥有和写动作同等地位的唯一方式。

### D0 · 范围：一个 change，两条链（实施期两次事实纠正）

**纠正一**：应答代码在本仓 —— `agent-runner/a2a.js` 的 `message/send` 分支里，`assistantMessage(contextId, out.text)` 就是那句话的出生点。不是「在别的仓」。

**纠正二**：`agent-runner/manager.js` 的 `turn()` 是所有回合的**唯一收口**（`message` / `message/stream` / `self` / 舰队回合全走它）。既然同一份代码、同一个收口，就**不该拆成两个 change** —— 拆开要把同一份契约写两遍，而两份契约必然漂移。

所以本 change 覆盖两条链：

| 链 | 位置 | 特点 |
|---|---|---|
| IM 出站 | `server/bots.js` | 同进程、有 cell DB，判定可直接调 |
| 门面/A2A 应答 | `agent-runner/manager.js` `turn()` 的出口 | 跨**进程**（runner 容器），无 cell DB |

差别只有一个：**裁决从哪来**。前者本地算，后者要问 cell。

**代价**：门面链的实现依赖一次跨进程往返，且必须失败关闭（取不到裁决就不发）。这比本地判定脆弱，所以它单独一组验收，不与 IM 链混在一起报。

### D2 · 旁路是「可检测」而不是「不可能」，并且要留痕

纯代码层面无法证明不存在旁路（任何地方都能直接 `fetch` 下游）。所以：
- 对外发送所需的凭据/端点**只**从执行路径的 `deps` 注入，模块级不保留可直连的配置；
- 任何未经闸的发送尝试在网关侧留一条「旁路尝试」记录并告警。

- **理由**：与其宣称「不可能」，不如让「发生了」可见。前者是一句无法验证的承诺。

### D3 · 台账加两列，不新建表

`principal`（代表谁，发布者身份戳）、`audience`（对象标识 + 渠道）。其余列复用 v116。

- **代价**：`action_audit` 继续变宽。可接受：窄表换来的是两本账对不上的风险，而审计的全部价值在于对得上。

### D4 · 内容只存 digest，原文由渠道侧保留

- **理由**：把「代理以你名义说过的话」在平台再存一份，等于凭空造出第二个敏感面。争议时需要原文，从渠道（IM/邮件）取——那里本来就有一份。
- **代价**：平台侧无法独立复现争议内容。这是刻意的取舍，必须写进运维说明。

### D5 · 身份口径是渲染层，不是内容层

同一份内容按受众渲染两种形态（内部带标注 / 外部不带）。审核对象是内容与授权，与形态无关。

- **否决**：给内外部各生成一份内容。两份内容会漂移，而「漂移的内容」正是最危险的东西——你批准的是 A，发出去的是 B。
- **回执按需**：MUST NOT 每条附声明。逐条声明会毁掉拟人体验，而拟人是对外代理的全部意义。这条取舍必须显式写在 spec 里（已写）。

### D6 · 放量按披露层级计样本

域整体一致率通过 ≠ 可以对外自动说话。原因：错误的代价按层级分布——财务层说错一句和内部层说错一句不是一个量级。所以升档条件加一条「本次命中的层级样本量达标」。

- **否决**：只按域一致率放量。那会让「内部话术很准」直接授权「对外报价自动化」，两个能力之间没有因果关系。

### D7 · 无反向能力的渠道恒不自动

撤销窗口不是贴心功能，是「先做后报」可信的前提。渠道撤不回 → 最高 `draft`，即使主人配了 `act-silent` 也在运行时回落。

- **理由**：这与 `add-personal-mandate` 的 D8 同源（撤不回的动作不许自动执行），只是把「动作」换成了「渠道」。

### D8 · 跨进程裁决走「runner 向 cell 取」，失败关闭

runner 侧不复制委托状（复制必然漂移，而漂移的授权等于没有授权）。每次对外应答前向 cell 取一次裁决：

- 取到 → 按裁决发 / 拦；
- 取不到（超时、5xx、网络）→ **不发**，按 `draft` 处理并把原文留给人。

- **否决**：在 runner 侧缓存策略副本。缓存的过期窗口就是越权窗口，而越权窗口无法被测试覆盖。
- **否决**：把裁决下推到 gateway。serving 面更早拒答很诱人，但 `message/stream` 的分块边界一旦切错，就会变成「前半句发了、后半句被拦」——比不发更糟。

**实施期补充（1.7 的真相）**：`message/stream` 是边生成边发的（`send("delta", …)`），出口闸拿到全文时前半句已经在对端了。所以流式与披露闸**在语义上不兼容**：
- 缓冲全部 delta 再一次性发 → 破坏流式存在的理由；
- 放行已发出的半句 → 破坏闸。

结论：**对外车道不提供流式**（`-32013`，在任何 spawn 之前拒绝）。这不是降级，是划界——能逐段评估的东西才能流式发。
- **代价**：每个对外回合多一次往返。可接受：对外发言不是高频路径，而正确性优先。

## Risks / Trade-offs

- **[拟人化对外不可逆]** → 可追溯优先于流畅：台账、回执、撤回窗口三件齐全才允许自动发送；层级样本闸挡住「刚学会就想上街」。
- **[披露误拦让代理显得不可用]** → 越界项结构化返回（可读、可改写重试）；连续越界计数进日报，避免静默失败被当成「它今天很安静」。
- **[台账无原文，争议时缺证据]** → 渠道侧保留原文；运维说明写明「要原文去渠道取」。
- **[旁路检测依赖网关]** → 凭据只在执行路径注入，模块级不留直连配置；检测留痕 + 告警，不宣称绝对无旁路。
- **[两套形态漂移]** → 形态是渲染层，内容只有一份（D5），漂移在结构上不可能。
- **[IM 渠道的反向能力参差]** → 按渠道声明 `revocable`；未声明的一律按不可撤回处理（默认保守）。

## Migration Plan

1. 台账加 `principal` / `audience` 两列（可空）。
2. 注册对外发言动作，但**默认不启用自动发送**：既有的门面应答走「生成 + 由主人发出」不变，只是每次应答开始写入台账（可观察，不改行为）。
3. 上线披露闸接线后，先以 `draft` 模式跑一段时间，收集各层级样本。
4. 回滚：动作条目可停用；两列可空、旧读面忽略；台账只增不减。

## Open Questions

- 各披露层级的样本阈值默认值（先给 20，与域一致率闸对齐）。
- `audience` 的对象标识是否统一（IM 用户 id / 邮件地址 / 访客 vid 三套），还是分层存。
- 回执的访问控制：对端凭引用即可查，还是需要一次性令牌。先给「引用 + 限时」，等真实争议场景再收紧。
