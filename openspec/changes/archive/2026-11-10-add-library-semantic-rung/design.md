## Context

见 proposal.md 的 Why。设计上约束现状：

- `document_chunks` 是 FTS5 虚表（`db.js` version 11），列 `text / doc_id UNINDEXED / name UNINDEXED / loc UNINDEXED`，默认 `unicode61` 分词器。虚表不支持 ALTER，改结构只能建新表重灌。
- `documents.source_text` 保留完整抽取正文，因此索引可随时从正文确定性地重建——这是迁移可以安全试错的前提。
- `searchLibrary`（`documents-search.js:97`）现状：先试 FTS5 MATCH；无命中且查询含非 ASCII 时落 `likeDocumentChunks`（`db.js:1841`）——`%整句%` 全表扫描、无排序、`LIMIT min(20,limit)` 取插入顺序前 N，`snippet` 固定 `substr(text,1,200)` 而非命中位置。
- **实测边界（2026-11-10，`data/app.db`，244 个切块）**：`unicode61` 把一段连续汉字当成**单个 token**，所以 FTS5 只在「查询恰好等于一个完整汉字段（被标点/空格/拉丁字母隔开）」时命中；一旦查询是更长汉字段里的子串就恒为 0。取 25 条长度 ≥8 的汉字段各截 4 字作子串查询，**25/25 全部 FTS=0 且 LIKE>0**。LIKE 路径返回的 rowid 严格升序，即插入顺序，无任何相关度排序。结论：中文的常规查询在现状下**全部**走无排序全表扫描。
- 平台目前**没有任何嵌入调用点**：`documents-search.js` 文件头明写 no LLM / no embedding provider。`grep` 全仓无 `/embeddings` 调用。
- 词元嵌入车道已在产（`ciyuan-embedding-lane`），契约规定维度是**调用方显式请求**的截断选项，默认取账号钉扎 provider 的原生维度（现 4096）——因此不传 `dimensions` 会拿到哪一维取决于账号配置，不能默认依赖。
- 记忆面的 `memory-digest-embed-lane` 已把「自适应预算 + 三档降级 + 慢样本如实记录」跑通，是纪律来源而非代码来源。
- SQLite 3.53.4（better-sqlite3 13），trigram 分词器可用（需 ≥ 3.34）。

## Goals / Non-Goals

**Goals:**

- 中文查询在**默认路径**上就有带排序的索引检索——不依赖任何开关与配置。
- 语义档作为可选增强，关闭时逐字节等价、零嵌入调用、零出网。
- 三档可观测：任何一次检索都能说出它实际走了哪条路，以及为什么降级。

**Non-Goals:**

- 不做跨 cell 检索、不引入 pgvector、不把资料库搬去 fd-text-core。
- 不引入中文分词原生依赖（jieba 类）——见 D2 备选。
- 不追求 1-2 字查询的召回质量，明示为已知边界。

## Decisions

### D1 中文词法档改用 trigram 分词器，新建表重灌后切换

**选择**：新建 `document_chunks_v2`（`tokenize='trigram'`），启动期从 `documents.source_text` 确定性重建切块与索引，校验条数与抽样一致后切换读路径；旧表保留一个发布周期作回滚。

**理由**：当前非 ASCII 路径违反 `document-search-index` 既有需求「ranked by full-text relevance」——LIKE 扫描无排序、按插入顺序截断，等于把「最相关」换成「最早入库」。trigram 让 CJK 走真正的索引 + BM25，且**仍然是本地、确定性、无 LLM**，与 `document-management` 的两条不依赖约束完全兼容。

**备选与否决**：
- 引入 `nodejieba` 类分词器获得更好的中文切分——否决：原生依赖要跨 darwin arm64 与 linux 双端编译，且把「确定性抽取」变成「依赖词典版本」，与既有契约的调性相反。
- 保留 LIKE 但按命中次数排序——否决：仍是全表扫描，不解决 O(n) 与无索引，且 snippet 仍不在命中处。
- 只对中文建 trigram、拉丁语系留 unicode61（双表）——否决（首版）：两套索引带来一致性与删除同步的双份风险，先用单表 trigram，若实测短查询退化明显再议。

**代价（必须写进文档而不是藏起来）**：trigram 对 1-2 字符查询无索引可用；索引体积约为原文的数倍。两者都在下面的 Risks 里有处置。

### D2 伴生向量表以 `(doc_id, loc)` 为键，不用 FTS5 rowid

**选择**：`document_chunk_vectors(doc_id, loc, model, dim, vector BLOB, updated_at)`，主键 `(doc_id, loc)`。

**理由**：FTS5 虚表的 rowid 在重建（D1 就会重建一次）后不保证稳定；`loc` 是切块在正文中的定位，重建后仍指向同一段文本，是唯一稳定的关联键。同时 `model` + `dim` 落库，使更换模型时可判定旧向量不可混用——这是 `align-ciyuan-embedding-dimension` 刚立下的口径。

**备选与否决**：把向量塞进切块表（新增 `embedding` 列）——否决：FTS5 虚表不能承载 BLOB 附加列且不支持 ALTER。

### D3 嵌入通道复用词元车道，新建平台侧客户端并显式请求维度

**选择**：新增一个进程内嵌入客户端，走词元的 OpenAI 兼容 `/embeddings`，**请求里显式带 `dimensions`** 并把 `model` 与 `dim` 一并落库。

**理由**：`ciyuan-embedding-lane` 的契约就是「维度在显式请求时才是契约，不传等于听账号配置」；不显式传，某天上游钉扎换 provider 就会静默换维，旧向量全不可比。

**备选与否决**：把资料库的嵌入委托给永忆服务——否决：永忆的页面模型是 L0-L3 记忆语义，资料库切块不是记忆条目，硬塞会污染它的蒸馏与去重逻辑。

### D4 融合用 RRF，不用加权分数和

**选择**：词法路与向量路各取前 K，按倒数排名融合（k=60），同一 `(doc_id, loc)` 两路命中则累加。

**理由**：BM25 与余弦相似度的分值量纲不可比，加权和需要跨语料调参且会随语料漂移；RRF 只用排名，无需归一化，是 `text-indexing-search` 已在用的口径——两族用同一融合机制，行为可对照。

### D5 档位按实际执行路径判定，不读配置

**选择**：档位在检索时由「查询向量是否取到」与「向量候选是否非空」决定，`hybrid` / `vector` / `keyword` 三值；通道故障与超时都落 `keyword` 并带降级成因。

**理由**：读配置会出现「配置说开了、实际降级了、界面还显示 hybrid」——这正是 `text-query-surface` 明令禁止的「部分数据冒充完整」在展示层的化身。

### D6 预算自适应，照纪律不照代码

**选择**：单次嵌入等待预算 = 近期成功耗时 p90 × 余量，clamp 在配置上下界；成功与超时样本都入库驱动下次预算；无样本用默认值。

**理由**：这是 `memory-digest-embed-lane` 已验过的形状（含「不因快样本塌缩到饿死慢请求」）。但**不复制那段实现**——它服务的是 digest 渲染，耦合了记忆渲染路径；资料库要一个只依赖分位数的最小实现。

### D7 回填以「向量缺失」为判据，幂等且可随时关闭

**选择**：回填扫描 `ready` 文档中缺少向量的切块，按批限速（每批 N 条 + 批间冷却），单文档失败记录后跳过。

**理由**：以「缺不缺」而非「跑没跑过」判定，天然幂等且中断可续——`text-corpus-store` 的 `content_hash` 幂等思路在这里的等价物。

### D8 成本按 cell 归集，开关即配额边界

**选择**：每次嵌入调用带发起 cell 的标识，供计量取数；关闭语义档立刻停止新调用，但保留向量。

**理由**：默认关闭意味着默认零成本；一旦开启，成本必须是可归集、可解释、可关停的，否则「免费自托管」的承诺会被一次误开打穿。

## Risks / Trade-offs

- **trigram 索引体积数倍膨胀，撞 cell 节点磁盘配额**（已有节点 DiskPressure 驱逐实录） → 迁移前先用代表性文档集量一次膨胀比，按 cell 文档上限估出最坏体积；超阈的 cell 拒绝开启语义档并给出实测数字，而不是等节点被驱逐。
- **重建索引期间并发写入** → 重建在启动期单事务完成，沿用既有 backfill 时机（进程尚未对外服务）；重建失败保留旧表并记 error，不让资料库整体不可用。
- **维度漂移导致旧向量不可用** → `model`+`dim` 落库，检索时只使用与当前配置一致的行；不一致时把该文档标为需重嵌，并在档位成因里体现，而不是静默返回低质量结果。
- **回填一次烧掉大量嵌入额度** → 限速 + 开关即停 + 开启前给出预估（文档数 × 切块数），由用户确认。
- **1-2 字查询在 trigram 下仍弱** → 在工具说明与设置页明示该边界；若实测影响大，下一刀再议前缀索引，本变更不假装解决。
- **语义档开启后单次检索延迟上升** → 预算 clamp 到配置上限，超预算即降级为词法并标注，MUST NOT 让检索挂住。
- **`search_library` 返回形状变化打破既有 agent 提示词** → 新字段只增不改；`keyword` 档的旧字段完全保留，旧调用方无需改动。

## Migration Plan

1. **中文词法（无开关，独立可回滚）**：建 `document_chunks_v2` → 启动期从 `source_text` 重建 → 条数与抽样校验 → 读路径切换。回滚 = 把读路径指回旧表；旧表保留一个发布周期后删除。
2. **语义档脚手架（默认关）**：伴生表迁移 + 嵌入客户端 + 工具返回新增档位字段（恒为 `keyword`）。此阶段线上行为除了中文排序变好以外不变。
3. **开启与回填**：资料库设置页开关 + 披露文案 + 存量回填（限速、可停）。逐库开启，不做全局默认。

## Open Questions

- trigram 索引在真实中文文档集上的膨胀比与 1-2 字查询的退化幅度——需要一次实测，结果只影响阈值与文案，不改契约。
- 是否需要对「已开启语义档但绑定未落库」的历史文档做一次性提示——可在实现时决定，不影响任务拆分。
