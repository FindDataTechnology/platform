## Context

见 `proposal.md - Why`。三条硬事实：

1. **房间事件流只有 SSE**：`gateway/zhiyu/index.js:851` 的 `GET /api/zhiyu/rooms/:id/events`。
2. **小程序的 `wx.request` 不支持流式响应**：没有 SSE。`Taro.connectSocket` 可用，但——见第 3 条。
3. **网关的 WS 升级把连接钉在调用者自己的 cell 上**（`gateway/index.js:1356-1390`：`registry.ensure(user)` 后
   `proxyUpgrade` 到该 cell）。房间是网关级跨 cell 对象，**不能直接复用这条升级路径**。

这三条合起来说明：移动端要的不是「再加个页面」，而是「另开一条与 SSE 同语义的传输」。而最便宜的那条
是**短轮询**，不是新 WS。

## Goals / Non-Goals

**Goals:**

- 移动端能进房、看流、说一句，语义与 web 一字不差。
- 传输降级可读、可恢复，且服务端不为客户端类型分支。
- 重交互不在移动端长出第二套语义。

**Non-Goals:**

- 不做移动端私窗、邀请、订阅管理（深链回 web）。
- 不重做 `/zhiyu` 首页的视觉系统（沿用 Card 原语与状态词表）。
- 不做离线消息队列（离线即补读，不本地排队发送）。
- 不新增网关级 WS 服务（本期不用 WS）。

## Decisions

### D1 — 短轮询承载，不长轮询、不新 WS

**决定**：新增 `GET /api/zhiyu/rooms/:id/stream?after=<seq>&wait=<ms>`：有增量立即返回，无增量短等（默认 10s）
后返回空增量。客户端在前端做退避（活跃 1s/静默 3s/后台暂停）。

**理由**：短轮询复用既有游标实现，服务端改动最小；WS 需要绕过「升级钉 cell」的既有结构（要么新开一个
网关级升级分支，要么做房间多路复用），代价远大于收益。轮询的代价是延迟与请求数——房间消息量低（人说话），
可接受。

**否决**：长轮询（连接占用大、与网关的连接数上限冲突）；网关级 WS（改动面大、与 cell 钉死结构冲突）。

### D2 — 抽出「游标 + 可见性」的共用实现，SSE 零改

**决定**：把「按 `after` 取窗口 + 可见性过滤 + 私窗归属」抽成一个函数，SSE 与轮询都调它。
SSE 的对外行为逐字节不变（由既有测试钉住）。

**理由**：两条传输各写一份过滤逻辑，必然在某个边界上分叉（私窗泄漏往往就发生在这种分叉里）。

### D3 — 客户端状态机进 `packages/core`

**决定**：`zhiyu-room-client.ts`：`seq` 去重、尾部起播、向前翻页、补读、本地可见性视图、传输适配器接口
（`open(cursor)` / `onBatch` / `close`）。三端各写一个薄传输适配器（web=SSE，移动=轮询）。

**理由**：与 `add-voice-input-mobile` 同一套理由——三份实现必然漂移，而漂移的表现是「某个端少数一条消息」，
极难发现。

### D4 — 精简面：一屏一房间

**决定**：移动端两页（列表 / 房间）。房间页 = 消息流 + 输入区（文本/按住说话）+ 底部一条「在场 N 人（只读）」。
私窗、邀请、订阅管理、房间设置 → 一次性链接回 web。

**理由**：三栏在 390px 上必然退化成抽屉套抽屉。深链回 web 的成本是一次点击，而在移动端重做一套交互
的成本是永久的双份维护。

### D5 — 深链用既有分享链接语义，不传长期凭据

**决定**：深链 = 一次性令牌（既有 `share-link` / `join/:token` 语义），web 侧换取会话后进入对应面板。

**理由**：移动端 token 与 web 会话是两套凭据；把移动端 token 放进 URL 等于把凭据写进浏览器历史与日志。

### D6 — 通知只带 `roomId` + `seq`

**决定**：订阅消息/推送的深链参数只有房间标识与消息位置，不含内容正文。

**理由**：通知内容会经过第三方通道（微信/APNs），正文外泄风险不可控；「点进去看」是更安全的默认。

## Risks / Trade-offs

- **[轮询延迟]** → 活跃期 1s 间隔；用户发消息后立即本地插入 + 立即拉一次，感知延迟 ≈ 0。
- **[轮询放大]** → 前台单房间单连接；切后台暂停；同一房间多标签去重（状态机单例）。
- **[深链回 web 的体验断裂]** → 明确文案「该操作在网页版完成」，不做半吊子移动版。
- **[移动端 token 与 web 会话不通用]** → 深链用一次性令牌，登录态各自独立。
- **[小程序页面集纪律]** → 两页必须静态注册进 `app.config.ts`（沿用 `docs/pageset-base-v1.md` §4），
  不动态装载。

## Migration Plan

1. 抽出共用游标实现 → SSE 回归全绿（零 diff）。
2. 上线轮询端点（web 不用，先给移动端）。
3. `packages/core` 客户端状态机 + web 适配器接管现有 SSE（回归钉住）。
4. 小程序两页 + 轮询适配器；App 两页 + 同适配器。
5. 通知模板与深链。
6. 回滚：移动端页面下线即回到今天；轮询端点留着无害。

## Open Questions

- 轮询间隔与 `wait` 的取值（1s/3s/10s 是一组经验起点，需按真实房间活跃度调）。
- App 推送通道（APNs/FCM）是否本期即接，还是先用「App 内未读 + 打开时补读」；本设计两者都成立，
  接不接推送不改变 spec。
