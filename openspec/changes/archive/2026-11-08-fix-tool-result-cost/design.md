# Design — fix-tool-result-cost

## D1 为什么先挑这两个工具

按实测体积排序，自家工具里 `fleet_turns_read`(2.3MB) 与 `memory_overview`(2.2MB) 最大，且**形态问题明确**：
一个是「全字段 + 美化缩进」，一个是「只按分区数判截断」。修它们不需要产品口径讨论，改的是输出形态。

`fleet_list`(1.7MB) 与 `cron_list`(1.3MB) 留到下一批——它们的正确页大小取决于使用场景（名册/定时列表
往往需要全量），需要先看清楚谁在调、调来干什么。

## D2 为什么美化缩进必须去掉

`JSON.stringify(x, null, 2)` 对「每条十几字段、每字段一行」的结构近乎翻倍。工具输出是喂模型的，
空格没有信息量。改用紧凑 JSON 是零语义损失的最大单项收益。

## D3 为什么错误串截 240 字

诊断需要的是错误的第一句（`turn timed out — context pressure (3 compactions)`），不是完整堆栈。
240 字足够覆盖本项目所有已知错误形态；超出部分每轮都在为它付费。

## D4 为什么 overview 要按「页数 > 已列标题」判截断

旧判据 `partitions.length >= 50` 只回答「分区多不多」。真正的信息损失发生在标题维度：
一个分区 100 页、概览列 3 条，读者会以为这就是该分区的全部内容。两个维度都设上限、
任一被裁剪即 truncated=true，才让「这是页」这件事对调用者可见。

## Risks

- R1 架构师少看到字段：`detail`（执行器归因的原始 blob）与 `traceTurnId` 不再随页下发。
  诊断所需的关键结论（errorKind / 错误首段 / 用量 / 链位）都在；需要 detail 时可走 cockpit 单轮详情。
- R2 页大小变化影响既有调用者：默认 50 → 20。`fleet_turns_read` 的唯一调用者是架构师 persona，
  其提示词不假设条数；且响应现在明说 truncated，模型可自行 `limit` 放大。
- R3 overview 标题 5 → 3：概览本身是罗盘，标题只用于「有没有这块内容」的判断。
