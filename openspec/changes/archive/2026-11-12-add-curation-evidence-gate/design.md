## Context

见 `proposal.md — Why`。三条约束来自现状：

- **`ecosystem-curation` 明写"实现权威在外部仓"**：过审流程、许可证裁决、出网白名单、容器托管都在 `mcp-gateway-registry`（部署在 `mcp.finddatatech.cloud` 之后），paas 只持跨仓契约与消费侧。所以**采集器不在本仓**——本变更只能定义"证据长什么样、缺了怎么办"。
- **目录条目由 `server/plugin-catalog.js` 归一化**：它已经把"读不到/坏 JSON"处理成诚实空目录（不是启动失败），并且三态（`enabled`/`available`/`unsupplied`）是**派生**的、请求状态不落库。证据态必须沿用同样的派生纪律。
- **台账是散文**：`docs/ecosystem-curation-ledger.md` 用 Markdown 表格维护，与目录条目没有机器关系——这正是"两份清单必有一份是假的"的结构。

## Goals / Non-Goals

**Goals**

- 证据可判定：缺哪一轴、缺什么钉点，机器能点出来。
- 台账成为生成物，手改即红。
- 人工填写与流水线写入同一形状，未接流水线的部署不被挡住。

**Non-Goals**

- 不在 paas 实现任何扫描器（许可证识别 / advisory / egress 分类 / 注入面启发式）。
- 不放宽准入原则（无社区直灌、无公开提交面），也不改首批数量上限。
- 不把证据变成"质量分级"承诺：证据只说明"审过什么"，不宣称"更好"。

## Decisions

**D1. 证据挂在条目上，不挂在台账上。**
替代方案：台账为源、条目引用台账行号。否决理由——条目要能在市场/供应面被机器读，台账是给人看的渲染物；反向依赖会让读面依赖一个 Markdown 文件。方向定为：条目 → 生成台账。

**D2. 证据态是派生的第三维，不是第四种供给态。**
理由：`enabled/available/unsupplied` 描述"这台部署有没有供给"，证据态描述"这条素材审没审完"，两者正交。混成一个枚举会让"未供给"与"缺证据"互相掩盖（`一个「启用」两个开关` 的同族错误）。因此读面同时给两个维度。

**D3. 拒绝点放在出片前置与上架路径，不放在读面。**
理由：读面必须能显示缺证据条目（否则运维看不见要修什么）；拒绝要发生在"它真的会生效"的两个口。

**D4. 台账生成用摘要判据，不用路径/time。**
理由：drift-guard 的既有盲点是"源路径硬编码"。生成物的摘要比对与源位置无关。

**D5. 证据里的审校人不进对外 annotation。**
理由：对外只出"审过 / 待复审 / 缺证据"与 SPDX、上游钉点；审校人是内部台账信息。

## Risks / Trade-offs

- **[既有条目全变"缺证据"，看起来像故障]** → 首次启用不删不改，只标状态并在出片前置点名；迁移步骤里给一份"待补清单"，让人按批补。
- **[人工填写被当成二等公民]** → spec 明写两种来源同形；测试里各有一条用例（手填通过与流水线写入通过）。
- **[证据过期导致出片被卡]** → `reviewValidUntil` 可空（永久有效），短周期条目才设期限；卡住时错误信息给出复审入口。
- **[生成台账把内部信息带出去]** → 生成器只输出许可范围内的字段白名单；审校人字段渲染为内部章节或省略。
- **[与外部仓的字段漂移]** → 证据形状在 paas 侧定义并作为契约；外部流水线按此形状写入，反向不成立（不接受"外部说我审过了"但没有逐轴字段）。

## Migration Plan

1. 目录 schema 加 `evidence`（可空），读面加证据态派生：此时所有既有条目显示 `缺证据`，不影响任何供给。
2. 出片前置接拒绝（先只警告一轮，观察期后再阻断）。
3. 台账生成器上线，CI 接摘要校验；手写台账改为生成物。
4. 回滚：生成器与 CI 步骤可摘，台账恢复手写；证据态降级为不显示；条目字段保留（无破坏）。

## Open Questions
