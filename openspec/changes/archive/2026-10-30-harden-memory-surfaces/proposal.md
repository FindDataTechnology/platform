# harden-memory-surfaces

## Why

两处「平时不出事、一出事查半天」的薄弱点，都是 2026-10-29 实战撞出来的：

**① digest 路由层零专项测试。** `src/http.ts` 906 行是全仓最大文件，却没有任何 `http*.test.ts`——路由层的输入边界只靠端到端偶然覆盖。当天那个「空查询被报成向量车道故障」的缺陷就藏在这里：没有一个测试断言过「空白 `q` 应该走哪一档」，于是它安静地跑进了生产，还污染了运维判断车道健康用的 `vector_ratio`。同类边界（缺 project、缺 rootKey、k/budget 越界、非法 tier、未授权 scope）目前全靠人工推理，属系统性缺口。

**② 向量全表扫描的规模假设没有闸门。** `db.allPageVectors()` 是 `SELECT ... WHERE model=?` 全表取回再逐条解 Float32Array，注释里写的假设是「页面数几十到几百」。当前最大单根 304 条、全局 1065 条，毫秒级、无问题。但这个假设没有任何监控：一旦某根涨到几千条，每次 digest 都要解几万个 float，症状会是「digest 变慢」——而这极易被误判成 embed 慢或上游慢（当天已经误判过一次上游）。**需要一条可在跨过阈值时亮灯的观测，而不是靠人某天想起来去看。**

## What Changes

- **digest 路由层边界测试**：为 `/digest`、`/pages/write`、`/pages/mutate`、`/memory` 的输入边界建专项测试，把「非法输入返回什么、合法但极端输入走哪条路径」钉死；优先覆盖已出过事故的空 `q` 一类。
- **向量规模观测**：在运维指标面暴露每根向量数、最大单根、以及「超过建议阈值」的标记；不改变检索实现，只让规模假设可观测。
- **阈值口径写进文档**：把「单根多少条以内是全表扫描的安全区」写成明确数字与依据，便于将来判断何时该换索引。
- **不做的**：本变更不改全表扫描为索引检索——当前规模不需要，过早优化会引入 ANN 近似误差，与「向量一致性」诉求冲突。

## Capabilities

### New Capabilities

- `memory-surface-hardening`: 记忆读面/写面的输入边界契约与向量规模的观测口径。

### Modified Capabilities

（无——本变更只新增观测与测试契约，不改变既有行为）

## Impact

- **fd-memory**：`src/test/`（新增 `http-routes.test.ts` 等）、`src/metrics.ts`（向量规模指标）、`src/db.ts`（可能需要一个轻量计数查询）。
- **paas**：`scripts/probe-embedding-lane.mjs` 增加规模门（可选，与既有探针同源）。
- **不受影响**：任何既有 API 的请求/响应形状、检索实现、存储 schema、tier/tag 语义。
- **无上产风险**：除指标字段外无行为变更；指标新增字段是纯增量。

## Open Questions

- 建议阈值取多少？当前最大 304、全局 1065。合理的报警线可能是「单根 > 2000」或「全局 > 20000」——需在实施时结合 digest 实测延迟曲线定，而不是拍一个数字。
