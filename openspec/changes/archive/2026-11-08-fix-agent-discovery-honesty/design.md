# Design — fix-agent-discovery-honesty

## D1 为什么抽成独立模块，而不是在两个文件里各改一遍

同一个谎说过两遍：路由给出没有总数的页，MCP 把那页的长度写成市场大小。两处各改一遍，
下一轮就各自漂移（这个仓已经栽过一次：`ops-console` 的两份代码）。所以把「匹配 + 排序 +
限幅 + 诚实计数 + 文案」放进 `server/agent-discovery.js`，路由与 MCP 都只引用它。

另一个现实约束：`server/delegation-mcp.js` **在 import 时就起 stdio 服务**，单测一导入就挂住
（本次实测 120s 超时 + "Promise resolution is still pending"）。把纯逻辑放进独立模块，
测试才可能覆盖它——不是洁癖，是可测性的必要条件。

## D2 为什么 `total` 必须是匹配数

`total: agents.length` 就是原来那个谎。`truncated` 让调用方能分辨「这就是全部」与
「这是一页」；两字段合起来才够——只给 `total` 而不给 `truncated`，调用方仍要自己比较大小。

## D3 为什么排序是契约的一部分

截断 + 不稳定排序 = 「你每次能看见的 8 个不一样」。按名称再按 id 排序后，同一批在线条目
无论 catalog 扫描顺序如何，得到的页完全相同；分页（limit）也随之可用。

## D4 为什么默认仍是 8

每条候选占一行 prompt 预算，`search_agents` 是给模型读的。默认 8 + 「可收窄/可分页」
比默认 50 更省，且诚实计数已经解决了「以为看见全部」的问题。上限 50 是防止一次把整个市场
灌进上下文。

## Risks

- R1 返回体多了 `total`/`truncated`：结构上是加字段，旧调用方（只读 `agents`）不受影响。
- R2 排序改变「前 8 个是谁」：这是**修**而不是**改行为契约**——旧序是扫描顺序，不是承诺。
- R3 工具描述变长：只多了一句截断说明与 limit 参数，仍在预算内。
