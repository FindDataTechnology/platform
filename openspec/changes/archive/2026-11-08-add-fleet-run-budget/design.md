# Design — add-fleet-run-budget

## D1 为什么执行点在点火，而不是在回合里

三个可选位置：

| 位置 | 能拦住什么 | 代价 |
|---|---|---|
| 回合执行中（每 N 秒查一次） | 连在飞的那一跳也能掐掉 | 要在热路径上引入周期检查与新的中止语义；把「预算」和「回合超时」两种失败混在一处 |
| run 收口时（settle） | 只能事后记账 | 拦不住任何东西 |
| **边点火（选它）** | 链的**继续** | 已起的跳照常跑完，但链不再生长 |

「整 run 预算」要防的是**链把花销放大**，不是「单跳跑太久」（那是 `budgetPerEdgeMin`）。
拦在点火处：语义单一（不点火 + 一条事实行），实现落在一个已有的纯函数附近，
且与既有的深度界、点火幂等闸**同一层**——三者在同一个 `for` 循环前依次判定，
不会出现「深度界拦了但预算没拦」的错位。

**副作用诚实记录**：已达上限时若仍有在飞任务，它们会跑完（已花的钱不浪费）。
要立刻掐掉在飞的，那是**停车入口**（D3）的职责，不是预算的。

## D2 计数口径：转弯行事实 + 在飞任务

```js
turnAdmission = runUsage(runId).turns + inflightOf(runId)
```

- **终态回合**取自 `member_turn_events WHERE run_id = ?`——`finalizeRun` 信的就是这张表，
  两处口径统一，不会出现「闸看到的数」与「收口算的数」不一致。
- **在飞任务**（`queued`/`running` 且 `origin.fleet.chain.runId` 相同）必须加进来：
  一波扇出会在同一个循环里连续建 N 个任务，若只读回合行，每个 hop 都会看到「还没到上限」
  而全部放行——闸就形同虚设。加在飞数正是为了让一次点火内的波次也被同一把尺子量。
- **token** 同理取自回合行（`usage_input + usage_output`，NULL 按 0 计），并同时暴露
  `unmeasuredTurns`，避免把「运行时没上报」误读成「花了 0」——上限判定仍按已知总量做，
  未上报的回合不虚构数值（与既有计量纪律一致）。
- **墙钟**用头行 `started_at` 到 `now`，不累计各回合时长（回合可并行，累计会翻倍）。

## D3 停车 = 头行两列 + 按 run 中止

`fleet_runs.status` 是**派生值**（`finalizeRun` 每次收口用回合行重算 ok/partial/failed）。
若把「已取消」写进 status，下一次 settle 会把它抹掉——所以停车事实落在**独立的两列**
`stopped_at` / `stop_reason` 上，`finalizeRun` 完全不碰它们（测试钉住）。

中止在飞回合用**既有**注册表 `ctx.taskTurnRegistry`（`cron-runner.js:1288` 建的
`activeTurns` 就是它，`worker-slots.js:85` 已在用同一条路）。按 run 精确定位的办法是：
遍历账本 open 句柄，取 `runId` 匹配者的 `sessionIds`（镜像会话 + 旋转子 id）逐个尝试。
生产里只有旋转子 id 真正挂着 collector，镜像那个自然返回 false——不用为「哪个是哪个」
额外记账。

被中止的回合落 `interrupted`（不是 `failed`）：这与「桥重启」同一语义，UI 给的是
「可重跑」而不是「报错」，正是「主人叫停」该有的样子。

## D4 幂等与原因保留

`stopRun` 是 `UPDATE … WHERE run_id = ? AND stopped_at IS NULL`，首次写入者胜。
预算触顶与主人取消可能竞争，谁先到谁的原因留下——这比「后写覆盖」诚实：
先发生的原因才是 explanation。路由对已停车的 run 直接回 `alreadyStopped: true`，
不重复中止（重复中止会打断用户后来手动重跑的新回合）。

## R1–R4

- **R1 既有舰队零变化**：未声明 `runBudget` → `normalizeRunBudget` 全 null →
  `runAdmissionBlocked` 在 stopped 检查后即返回 null（**唯一新增开销是一次头行读取**）。
  另外，未知 run（无头行，例如老数据/纯手工任务）**永不拦截**——闸不能因为读不到账
  就挡住工作。
- **R2 畸形声明**：`runBudget: 5`、`{}`、`{maxUsd: 3}` 全部结构化拒绝。空对象拒绝是有意的：
  写了 `runBudget` 却没有任何上限，多半是笔误，静默放行会让舰队以为有闸。
- **R3 计数漂移**：`runUsage` 每次现算（SUM），不维护计数器，故不存在计数器漂移；
  代价是一次 SQL，与点火同频，可接受。
- **R4 与点火幂等的关系**：停车/预算拦截发生在幂等判**之前**——一个已停车的 run 重复
  进入点火，既不建任务，也不写第二组「点火被拒」行……**注意**：当前实现对每次进入都会写
  一条拒绝行。这是有意的（每次被拒都是一次真实尝试，可审计），但会随重试增多；
  若将来嫌吵，可按 run 去重，属可选优化，不影响正确性。
