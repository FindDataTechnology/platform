## Context

见 `proposal.md`「Why」。设计相关现状：

- `facet/marketplace-json.js` 已有一份 Claude 形态的端点实现：`loadListed(viewer)` 负责收录
  （公开 ∧ 非 unlisted ∧ 策展，算子白名单覆写），随即就地映射成 `plugins[]` 并逐文件提供插件树。
  **这段过滤逻辑目前闭在路由注册函数里**，外部拿不到。
- 包内容取自已发布版本快照，路径安全统一走 `lib/skill-files.js`（`safePackagePath`、
  文本/脚本判定、包限额）。
- 客户端事实（一手，2026-10-30）：插件清单在 `.codebuddy-plugin/plugin.json`、
  `.workbuddy-plugin/plugin.json`、`.claude-plugin/plugin.json` 三处**等价**；市场清单
  `.codebuddy-plugin/marketplace.json` 结构为 `{name, owner, plugins:[{name, source, description, version}]}`；
  `source` 支持相对路径 / GitHub / Git URL。官方文档明写：URL 型市场只取 `marketplace.json` 与
  相对路径条目的 `plugin.json`，「无法通过 HTTP 目录列表递归镜像任意插件文件」，含
  技能/命令/Hooks 的插件必须走 Git/NPM 源或整仓 Git/ZIP。

## Goals / Non-Goals

**Goals**

- 一份可被「添加地址」的 Git 市场仓，装进去就带技能与智能体，不需要客户端再取任何插件文件。
- 收录口径与浏览面/Claude 端点**同源**，三处不可能给出不同的在册集合。
- 生成失败绝不影响线上：last-good 语义。

**Non-Goals**

- 不做 ZIP 分发（Git 已足够；ZIP 的新鲜度语义更绕）。
- 不做"提交进他们的官方市场"（他们没有自助提交口）。
- 不动订阅/购买/部署语义——市场仓只是发现与安装面的另一个出口。

## Decisions

### D1：Git 仓库，而不是再来一个 HTTP 端点

客户端文档已把 HTTP 型市场的边界写死（只取两个 JSON，插件文件不取）。再造一个端点等于造一个
装不上的市场。仓库形态天然满足"整仓物化 + 版本钉扎"。

**Alternatives**：HTTP 端点 + 每个条目声明 GitHub 源——需要给每个包建仓，成本随包数线性增长；
ZIP 快照——新鲜度判定依赖 ETag/版本文件，运维面更脆。

### D2：收录逻辑抽出来共享，不复制

把 `loadListed` 从 `registerMarketplaceJson` 的闭包里提到模块级导出，端点与仓库生成器**调用同一个
函数**。理由：收录口径已经有过一次"清单与浏览面不一致"的历史（策展接线），第二个副本必然再漂一次。

### D3：清单落在 `.codebuddy-plugin/`，不写三份

客户端三处等价，但仓库面向的是 WorkBuddy/CodeBuddy 族；写一份 `.codebuddy-plugin/plugin.json` 即可，
不为了"兼容更多"同时放三份（三份会带来"哪份是真的"的歧义，且用户改一份就静默失效）。

### D4：MCP 仍然只做指引

与 Claude 端点同一姿态：插件 README 给端点与凭据说明，**插件清单里不出现 `mcpServers`**。
两条理由：仓库是公开可匿名的，任何嵌进去的服务器配置都会变成"没有 key 就装坏"的插件；
以及"插件声明的 `mcpServers` 能否触发客户端的 OAuth 发现"尚未真机验证——验过再升级，不先猜。

### D5：全量重建 + 原子替换 + 内容不变则不提交

生成流程：写到临时目录 → 自检（清单可解析、每个条目目录存在、路径不逃逸）→ 原子替换工作树 →
`git commit`（内容无变化时 no-op，不产生空提交）→ 推送。失败时工作树保持上一份，客户端继续拿 last-good。

**Alternatives**：增量更新单个包目录——需要维护"仓内状态 vs 注册表状态"的映射，失败恢复更复杂，
收益只是省几秒。

### D6：刷新是运营动作，不在发布请求路径上

发布接口是热的（作者点一下就要回），推仓是慢的且需要推送凭据。因此刷新由脚本触发：运营在发布/改策展后
跑一次，或挂一个低频定时。刷新上界（≤ 一个周期）写进运维文档，不承诺实时。

### D7：仓里只放包内容，不放任何凭据

生成器对每个文件走 `safePackagePath` 与限额；README 里的连接指引只写端点和"需要调用键"，
不出现任何 key 形态的串。CI 侧再加一条正则扫描（`wgk-`/`sk-`/`skh_` 前缀）兜底。

## Risks / Trade-offs

- **UGC 进公开仓**：unlisted/private 会立刻从仓里消失，但**已装到用户机器上的副本收不回来**。
  → 与 Claude 端点同一诚实边界，在指南里写明；下架语义按"停止分发"而非"远程删除"。
- **仓库体积随包数增长**：只放文本类技能文件（既有包限额已约束单包大小），并禁止二进制。
  → 超限包在生成时报错点名，不静默截断。
- **推送凭据泄漏**：沿用既有发布通道的环境注入方式，凭据不入库；仓内内容过正则扫描。
- **口径漂移**：靠 D2 的共享函数 + 一条断言"仓内清单集合 == 端点清单集合"来钉死。
- **作者的私有包误入**：生成前按设计 D2 的同一函数取集合，且加一条"仓内目录必须全部在册"的反向断言
  （防止旧目录残留造成越权分发）。

## Migration Plan

1. 首次生成到空仓即可，无数据迁移；已有 Claude 端点用户零影响。
2. 回滚：`git revert` 上一个快照提交，或停止刷新——仓保持在最后一个 commit，客户端照常工作。
3. 顺序：先跑通"生成 + 自检"（不推送），再接通推送；兄弟单 `add-workbuddy-mcp-lane` 不依赖本单。
