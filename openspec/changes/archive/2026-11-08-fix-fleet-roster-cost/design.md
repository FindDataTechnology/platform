# Design — fix-fleet-roster-cost

## D1 为什么名册不像 turns 那样默认分页

`fleet_turns_read` 是「最近的失败有哪些」——分页天然（时间序，越近越相关）。
`fleet_list` 是「我有哪几支舰队」——**漏一条就是错误陈述**：架构师会据此判断某舰队不存在，
进而在 `fleet_draft` 里重建它。所以名册默认全量；省体积靠**投影 + 紧凑**，不靠砍条数。

## D2 为什么仍要一个硬上限

200 行是「病态 owner」的护栏（脚本化创建舰队、导入事故）。它不是分页机制：
正常 owner 永远碰不到，碰到时 `total`/`truncated` 会明说。

## D3 为什么只留六个字段

路由返回的就是这六个；`orchestration` 等重字段本来只在 `fleet_spec_read`（单舰队全 spec）里给。
名册是索引，不是规格——把规格塞进索引会让每次「我有哪几支舰队」都付一遍全量体量。

## Risks

- R1 调用者依赖美化格式：模型读紧凑 JSON 没有损失（空格不携带信息）。
- R2 上限误伤：200 远超实测最大值 57（14 个 cell 全量统计），且超限明示。
