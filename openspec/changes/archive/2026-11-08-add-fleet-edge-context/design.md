# Design — add-fleet-edge-context

## D1 为什么要**第二个**占位符，而不是复用 `{{fleetContext}}`

复用会让边回合直接吃下巡视段，而巡视段最后两段是：

- 「（以上为系统注入的巡视上下文，供你巡视与决策参考。）」
- 巡逻纪律：「**先报数再补充**：读完上下文就调用 report_status 交本轮的数……空手超时
  是最差结局」

对一条「上游刚把活交给你」的接棒回合，这是**反向指令**——它会照着报数、然后把真正的
任务放过去。所以不是"同段不同长"，是两种语义：巡视段的收尾是"以报数为交付"，边回合的
收尾是"任务在上文，背景在下面"。

两个占位符也让渲染契约显式化：`{{fleetContext}}` → patrol，`{{fleetEdgeContext}}` →
edge，读 prompt 就知道会拿到什么。

## D2 edge 模式的三个差异（以及为什么只这三个）

1. **去掉巡逻纪律尾段**，换成一句「（以上为平台注入的集群背景，本轮要做的任务见上文指令。）」
   —— 理由见 D1。
2. **不渲染决策送达段**。`decisionDigest` 渲染的是"本岗未送达的裁决"，而送达是一条
   **义务**：读了就可能被标记为已送达（决策车道 `pendingDeliveryFor` 的语义）。边回合
   不是巡视轮，让它在倾倒 brief 的间隙顺手消费掉裁决，等于把裁决弄丢。因此 edge 模式
   连 provider 都不调用（测试断言 `decisionDigest` 调用次数为 0）。
3. **总量池 24KB → 8KB**（`EDGE_TOTAL_LIMIT`）。边回合已有自己的主料（brief 4000 字 /
   上游结果 2000 字 / 唤醒消息 4000 字），舰队背景是"知道组织长什么样"，不是"本轮素材"。
   每投 4KB、总量 8KB 的量级足够放下 2-3 个下级 + 自己的往轮，又不会把主料挤出注意力。

其余全部复用：下级报数段、本岗往轮段、近期执行健康段、记忆与知识段、以及既有的
"下级优先、本岗按剩余预算截断并标记"的顺序。

## D3 只给 persona 目标加 token

- **a2a**：目标是另一个服务（可能有自己的上下文与记忆），塞一段本舰队的巡视材料既越界
  也无用。
- **tool**：tool 岗的 prompt **就是它的 JSON 参数**（`fleets.js:1075-1082` 已经强制
  `JSON.parse` 校验）。追加任何文本都会让 JSON 非法。这一条有测试逐字节钉住。

tool 目标在接棒/扇出里不出现（`if (target.targetKind === "cluster") continue` 之外，
handoff/fanout 的 target 域是 persona/a2a），但 dispatch 与唤醒的 target 域包含 tool，
所以两处都显式判了 persona。

## R1–R4

- **R1 双重注入**：既有条款"注入对每次执行恰好发生一次"仍由同一个缝保证；edge token 与
  patrol token 同时出现时各渲染一次、各自替换（测试覆盖）。
- **R2 渲染失败**：与巡视轮同姿势——抛错 → 该次执行落 failed，不静默裸跑。边回合失败
  的代价是这条边断掉，比让下游在无感知下拿到残缺背景更诚实。
- **R3 `$` 注入**：`String.replace` 的字符串替换会把段内的 `$&`/`$'` 当模式。报数文本里
  有金额（`$309`），所以两处替换都改用函数 replacer。
- **R4 上下文体积**：8KB 上限由 `EDGE_TOTAL_LIMIT` 一处控制；本岗块仍走既有的
  `SELF_HISTORY_MAX_CHARS ≤ TOTAL` 预算不变量检查（该检查针对 24KB 常量，edge 更小故
  仍然成立）。
