# Proposal: add-rollout-gap-durability

## Why

平台滚版当前是 `Recreate` 策略（hostNetwork 钉死 3100 端口，旧 pod 必须先死新 pod 才能起）——每次
bump 都有 1.5–3 分钟全平台不接客窗口。窗口内三种行为并存：舰队 cron 回合已有 P2 停机补拍（2× 周期
容差窗），回合台账有 sweepOpenRuns 兜底收孤儿；但两条缝仍在**静默丢**：

1. **bot 回调缝隙丢**（§10-31 bot 回复可信化班在册挂账）：死窗期到达的外部平台回调（企微/飞书/
   Telegram/公众号）连接被拒无人接听；启动窗的 bootBuffer 是**内存态且有上限**（BOOT_BUFFER_MAX，
   满则 503 直弃），SIGKILL 时缓冲一并丢；无任何平台消息幂等层——即便上游重试/人工重放也无法安全
   处理，这正是"缝隙丢消息"的根因。
2. **滚版打断的回合节拍静默消耗**：in-flight 回合被 SIGKILL 后 sweep 标记如实，但该次 cron 节拍
   已按"已触发"记账（lastRun 在点火时落），不进停机补拍——该岗位这个节拍丢了，事后无人知、无人补。

本变更治"丢"（把丢变延迟/如实补），**不含** Recreate→滚动/双活改造（hostPort 解绑属后续独立
变更，见台账 §15.121 续九的分析）。

## What Changes

- **bot 回调持久受理**：webhook 验签后**先落盘后处理**（write-ahead 受理队列，磁盘而非内存），
  应答平台在持久化完成后立即返回，处理异步进行；重启后未处理受理项被接管补处理。bootBuffer
  从内存态改为盘上受理队列的一部分（上限从"丢弃"变"落盘"）。
- **平台消息幂等**：按平台消息标识（企微 MsgId 等，各适配器已有解析面）建幂等键，重复投递
  （上游重试、边缘重放、受理补处理重叠）MUST NOT 产生第二次 agent 回合；幂等键保留窗口与
  受理队列同生命周期。
- **打断回合容差补拍**：启动清扫把"滚版打断"的 open run（sweepOpenRuns 判定）按既有停机补拍
  同一容差规则（2× 周期、地板 6h、PLATFORM_CRON_CATCHUP=0 杀开关）补一拍并留痕；窗外如实
  记 missed 不补。
- 死窗期（无监听）回调仍依赖平台侧重试语义——本变更保证**重放安全**（幂等），把"丢"收敛为
  "延迟到平台重试或人工重放"。

## Capabilities

### Modified

- `social-bot-channels` — webhook 受理需求 ADDED 持久受理+幂等场景组（受理先行/重复投递不二跑/
  重启接管补处理）。
- `agent-fleet-runs` — run 生命周期需求 ADDED 打断补拍场景组（容差窗内补拍/窗外如实 missed/
  杀开关沿用）。
