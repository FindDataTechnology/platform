## Context

见 `proposal.md` — Why。四条现状约束决定做法：

1. **域枚举已封闭**（`lib/personal-mandate.js` 的 `DOMAINS`，未知域名拒绝）。`add-personal-mandate` 立了四域，本 change 只能往里喂事项，不能加第五个——否则设置面、迁移、判例分级全要跟着动一遍。
2. **委托策略按类别路由**（`server/routes/fleets-db.js` 的 `routeForItem`，类别 ∈ routine-ops/infra-ticket/config-change/hr/spend，其中三类硬锁 owner）。这是 `ops` 域的内部语言，不适合当个人事务的坐标系。
3. **判例读取今天是硬过滤**（`server/routes/fleets.js` 取 `resolvedBy === "owner" && state === "delivered"` 的前 3 条）。要加分级就必须改这个查询，而它是 deputy 判断质量的唯一约束，改错方向就是自我强化。
4. **名册的 targetKind 是封闭联合**（`persona`/`cluster`/`a2a`/`tool`），新增 `auditor` 需要同时改 schema 校验、工具面治理与模板。

## Goals / Non-Goals

**Goals:**

- 三类个人事务真的流进已有域，且流向可关可改（声明式，不散落在代码里）。
- 判例分级由**服务端按产生路径**判定，代理无法自报等级。
- 审计官的否决是**执行路径上的强制分支**，不是提示词建议。
- 更正建立「候选规则」而不是直接改行为——与 `persona-self-evolution` 同一条纪律。

**Non-Goals:**

- 不做对外发送与披露（`add-principal-disclosure-gate`）。
- 不做跨用户判例共享／判例市场。
- 不做审计官的模型自迭代（它自己也需要被审）。
- 不新增域枚举，不改 `DOMAINS`。

## Decisions

### D1 · 事项接入用「映射表」而不是新类别

域内事项的坐标系是「事件源 → 域」，不是委托策略那套 category。实现为一条声明（存 cell 设置）：`{source: 'cross-line-blocker' | 'supplier-thread' | 'people-schedule', domain, enabled, filter?}`。

- **否决**：给 `decision_items` 加个人事务专用类别。那会让 `routeForItem` 的类别集合膨胀，而它同时被 `ops` 域的委派语义使用——两套语义挤在一个枚举里，等价性测试立刻失效。
- **理由**：映射是数据，改它不需要发版；委托策略的 category 是舰队内部语言的合同，不该被个人事务污染。

### D2 · 判例等级由产生路径判定，落 `decision_items` 新列

判定规则（服务端，不看内容）：

| 产生路径 | 等级 |
|---|---|
| 主人在无代理草稿的情况下手写/亲答 | `owner-authored` |
| 代理产出草稿，主人**未修改**发出 | `owner-approved` |
| 代理自行裁决 | `deputy-ruled` |

- **关键**：`owner-approved` 的判定必须比对草稿与最终发出的内容。若只按「主人点了发送」判定，等于把代理的话记成主人的话。
- **否决**：让代理在提交时标注等级。自报在信任模型里等于没有。

### D3 · 审计官是舰队岗位，不是独立服务

复用 `agent-fleet-core` 的岗位/节奏/报数；新增 `targetKind: auditor`。

- 工具面：读判例、读决策历史、读记忆、提交结论。**没有**写工具、没有发送工具——由服务端在岗位保存时校验（写工具在名单里就拒绝）。
- 结论三态里只有「阻断」需要服务端强制：`同意`/`有异议但放行` 都是放行，区别只在是否留痕。
- **否决**：让审计官作为「第二模型调用」内嵌在 delegate 里。那样它的输入由调用方拼装，反例注入就不可保证——而反例正是它唯一的价值来源。

### D4 · 反例注入是硬拼装，不是提示词建议

审计官上下文的构造里，**固定**拼入主人推翻过的最近 N 条（N 默认 5，可配），且 N 条为空时结论必须带「无反例可用」标注。

- **理由**：没有反例的审计官会与专家同向走偏（两者都只看到「主人以前同意过什么」）。标注是为了让主人知道这条结论未被反向检验过，而不是让它看起来一样可靠。

### D5 · 更正蒸馏沿用自进化的**纪律**，但不共用它的表（实施期修订）

`persona-self-evolution` 的纪律是「修订由提议产生、永不直接生效、人终审」。候选判例严格照此执行：`candidate → (人批) → approved` 才可引用，`rejected` 永不生效且理由保留。

但**表不共用**。`persona_candidates` 是按「可解析的 persona + persona 正文」建模的：`currentPersonaFor` 要求目标能解析，`createCandidate` 还会跑文本 sanity 扫描、`markPromoted` 要求先过 A/B 评测。判例规则既没有 persona，也没有「原文可 diff」，塞进去只能靠伪造 targetKind 或放宽那张表的约束——两者都会把一条已经在产的管道搞脏。

所以：独立表 `precedent_candidates`，同一套纪律，`(fleet_id, rule_key)` 唯一索引承担去重，`reject_reason` 供审计官读取。

- **理由**：纪律要一致，模型不必硬合并。共用表省下的是一张表的 DDL，付出的是两条管道互相污染。
- **后果**：设置面要展示两处提案（persona 修订 / 判例候选），这是诚实的成本。

### D6 · 个人域用额度替代类别禁令，且额度缺失时保守回落

`ops` 保留三类硬锁；其余域不按类别禁用。`cost` 类动作在个人域若无额度声明，回落 `draft`。

- **理由**：「花钱」在个人事务里是最常见的委托对象；不可委托的是「超过额度的花钱」。缺额度时保守是唯一安全方向。

### D7 · 放量由一致率闸控制，闸在服务端

一致率 = 代理判断与主人实际判断吻合数 / 可比样本数。样本只取「主人事后真的改过或确认过」的事项。升到 `act-notify` 时服务端校验阈值与最小样本量。

- **否决**：只在 UI 上提示一致率。提示词/界面提醒会被忽略，而升档是不可逆的信任扩张。

## Risks / Trade-offs

- **[审计官与专家同向走偏]** → 反例注入（D4）+ 允许审计官独立配置模型；结论里的「无反例可用」标注让未被检验的结论可识别。
- **[判例分级判错方向]** → 等级由产生路径判定（D2）+ 草稿/终稿比对；`deputy-ruled` 永不入判例集，宁可判例变少。
- **[映射表变成隐蔽的自动化开关]** → 映射只决定「事项进哪个域」，域的模式仍由委托状决定；未配置模式即 advise。
- **[审计官成为瓶颈]** → 它只对已由代理提出的判断做复核，不是每条事项都要过；且「有异议但放行」不阻塞。
- **[一致率统计自我循环]** → 样本只取主人有实际判断的事项；代理自裁的单子不计入分子，避免用代理自己的判断证明代理自己可靠。
- **[targetKind 联合扩展影响既有读面]** → 所有消费点按未知类型兜底（不崩、不误判），并由测试钉住既有四类行为不变。

## Migration Plan

1. `decision_items` 加列（`precedent_grade`、`auditor_verdict`、`auditor_note`），全部可空。
   - **存量回填方向必须保守**：今天的记录无法分辨「主人手打」还是「原样发了代理的稿」，因此存量一律记为 `deputy-ruled`（不入判例集）。
   - 代价：上线后可用判例会**变少**（现有 deputy 的判例面缩水）。这是有意的取舍——判例变少只降低代理能力，判例变脏会放大错误。这条必须写进上线说明，否则会被当成功能退化。
2. 上线映射表（默认空 → 无事项流入，行为不变）。
3. 上线 `auditor` 岗位模板与工具面校验；未创建的舰队不受影响。
4. 回滚：删除映射即停流；新列可空、旧读面忽略；`auditor` 岗位可停用不影响其他类型。
