## Context

见 `proposal.md — Why`。三条既有事实决定了实现形状：

- **供给单位是部署**：`dsh-plugin-supply` 的供给声明 = profile 模板的 manifest bundle 列表 + dsh 安装矩阵；插件只在镜像/桌面发行期烘入。roster 的读面已经存在（`server/plugin-catalog.js` 的三态 `enabled` / `available` / `unsupplied`），团队声明必须复用这三态，而不是造第四种。
- **团队由模板落地**：`POST /api/fleets/from-template` 是唯一建队入口，新生一律 `paused`（`fleet-is-the-team-pack-is-the-mold` 的判断）。补丁行应在这一步写，而不是在回合执行前临时拼。
- **补丁层是单一作者**：`dsh-profile.js` 以"读—过滤—追加—原子写"维护 `cordis.patch.yml`，并已支持热应用。团队插件行必须走同一写入口，不能由第二个模块直接改文件（否则两个作者的过滤规则会互相抹掉对方的行）。

## Goals / Non-Goals

**Goals**

- 团队制品自足：包在手 = 知道它要哪些插件，且落地不需要网络。
- 一个团队一个补丁行、多团队共享一份烘入副本、归档时按"还有谁在声明"决定是否移除。
- 缺料一律明确失败，不出现"装好了但插件没生效"的静默状态。

**Non-Goals**

- 不做团队级安装或版本管理（版本只能断言，不能选择）。
- 不把插件声明下放到**席位级**：工具面才是席位级的（`agents[].resources.mcpTools`），插件是团队级服务。两者不混。
- 不改 `dsh-plugin-supply` 的审批与烘入流程。

## Decisions

**D1. 声明写在 pack（模具），落在团队实例（运行时），不写进市场发布面的"供给声明"。**
替代理由：把插件写进发布面会让"装了这个包"等价于"这台机器要装这个插件"，与"供给是运维决定"冲突。D1 保持了 `catalogue 成员 ≠ 供给声明` 的既有纪律——这里多一层：`pack 声明 ≠ 本机供给`，缺料即失败。

**D2. 补丁行的写入集中在 `dsh-profile.js` 的既有写入口，团队插件作为"来源标记的一类行"。**
替代方案：`server/fleet-plugins.js` 直接改 YAML。否决理由——同族事故（两个作者互相过滤）已经在别处发生过；行必须带来源（`origin: fleet:<id>`）以便按"还有谁声明"决定移除。

**D3. 幂等靠"按来源重算"，不靠"跳过已存在"。**
理由：跳过式幂等会在"声明变更"（团队换了插件）时留下旧行。正确做法是每次落地重算该来源应有的集合，多退少补。

**D4. 版本断言优先于语义化比较。**
理由：roster 里每个 id 只有一个烘入版本；因此"版本不符"只可能是"声明写错了"或"机器没升级"，两种都要人看，不该自动择近。简单的字符串相等即可，不做 semver 区间。

**D5. 读面的"生效集合"由补丁层实时派生，不落库。**
理由：落库会与"补丁层是唯一事实"分叉（配置值被快照那类教训）。来源标记从行的 `origin` 读。

## 偏离与理由（实施记录，2026-11-12）

**D2 的 `origin: fleet:<id>` 字段 → 同目录台账 `fleet-plugins.json`。**

原设计要在补丁行上带 `origin` 以便按"还有谁声明"决定移除。实施时发现补丁行是 **cordis loader entry**：它只认 `id` / `name` / `config` 等 loader 字段，多一个未知键是**装载期风险**（可能整行被拒或整份 patch 报错），而我们无法在不部署的情况下证明上游容忍它。

改法：行保持最纯的 `{ id, name }`（与脚手架插入 `sdk-jsonrpc-server` 完全同形），"谁声明了它"写进 `profiles/<name>/fleet-plugins.json`：

```json
{ "version": 1, "plugins": { "pdf-kit": { "name": "pdf-kit", "fleets": ["f1","f2"] } } }
```

台账每次落地**重算重写**（不是追加），所以它不可能与声明漂移；写补丁与写台账由同一个函数（`writeFleetPluginRows`）原子先后完成，且都在 `dsh-profile.js` 这唯一作者之内。读面认"台账 ∩ 补丁行"——手改补丁塞进来的行不会被当成团队插件。

代价：两个文件而不是一个，且二者必须同时写（已由单一写入口保证）。收益：不给 loader 引入任何未知键。

## Risks / Trade-offs

- **[团队归档时误删别人要用的行]** → D2 的来源标记 + "还有谁在声明"的引用计数；测试覆盖 A/B 共享场景。
- **[补丁层的团队行被平台写入抹掉]** → `writeLlmProfile` 的过滤只针对 `llm-pi-ai` / `spill-policy` 两个 id，团队行不受影响；新增一条回归断言防止未来有人扩大过滤范围。
- **[声明与实际不一致（roster 升级后 id 消失）]** → 读面标"未供给"，落地时不静默跳过；升级 roster 前跑一次全量团队的缺料检查。
- **[8 项上限不够]** → 上限是政策值（同 `maxMcpRefs` 的既有做法），可由运营者调；不是结构限制。
- **[断网落地依赖"烘入副本存在"]** → 落地只写补丁行、不碰包体；包体存在性由供给面保证，落地阶段只做 id 校验。

## Migration Plan

1. 校验与读面先行：`plugins` 可声明、可校验、可在读面显示（此时落地还不写补丁行，团队行为不变）。
2. 落地接 `from-template` 与归档清理；先在单团队验证，再多团队共享场景。
3. 导出/导入的缺失校验接上。
4. 回滚：落地路径可摘（声明仍可校验但无效果），读面回退为不显示插件栏；无数据迁移。

## Open Questions

- 团队换插件时是否需要"先停团队"的提示（当前设计为直接多退少补，运行中团队的下一回合生效）。可在 apply 阶段按实测决定是否加提示。
