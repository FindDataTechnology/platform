# Design — fix-cron-list-scope

## D1 为什么默认排除舰队物化任务

实测构成：774 个任务里 658 个（85%）是舰队岗位的节奏任务。它们由舰队创建、随舰队变更、在舰队面可读
（`fleet_list` 给名册、`fleet_spec_read` 给每岗 cadence）。它们出现在「定时任务列表」里是**存储形状的泄漏**，
不是用户心智里的「我的定时任务」。

## D2 为什么必须显式报出被排除的量

默认收窄的风险是「用户以为没有了」。头部那句 `774 total: 116 operator, 658 fleet-materialized` 同时给出
两个口径与总量，并把 `next offset` 印出来——收窄是**视图**，不是**隐藏**。这与本仓反复出现的
「页冒充全量」是同一类问题，处理方式也一致：说清楚。

## D3 为什么分页默认 30 而不是 50/100

116 条操作者任务紧凑渲染约 20KB；30 条约 5KB。默认值服务的问题是「我有哪几个任务」，
而不是「把 116 个全列给我」。真要看全时 offset 分页或 `scope=all` + `limit=200` 都能到。

## D4 为什么未知 scope 回落到 user

`scope=bogus` 若被当成 `all`，一次拼写错误就会把 800 行倒进上下文。回落到最窄的合法值，
配合头部的全量账目，错误可见且代价最小。

## Risks

- R1 既有调用者假设全量：`cron_list` 的调用方是 agent 侧工具面；默认从「全部」变成「操作者任务」是**语义收窄**，
  已由头部账目兜底（想看全量一句话即可）。
- R2 舰队任务排查变两步：先 `scope=fleet`，需要上下文再 `fleet_spec_read`。两步换来的是默认路径便宜 6 倍。
