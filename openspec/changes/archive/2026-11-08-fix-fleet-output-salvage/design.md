# Design — fix-fleet-output-salvage

## D1 为什么先「点名」而不先「调大预算」

调预算（600s → 1200s）能让一部分回合跑完，但它只把墙推远：压在 600s 的那批，工作集已经超出窗口，再给 10 分钟多半会再压缩几轮然后照样超时，同时把单轮成本翻倍、把串行队列堵得更久。
先做的是**让失败说实话**：`contextPressure` + 压缩次数。有了这个字段，主人才分得清「这个岗位需要更长的预算」和「这个岗位的任务本身太大，得拆」——这是两种完全不同的处置。

## D2 为什么收尾问的是「同一子会话」

同一子会话里还留着本轮已经取回的全部材料（它只是被压缩过，并没有丢）。换成新会话就得重做全部工作——那正是我们要避免的重复花钱。所以收尾 prompt 明确：「只调用 `report_status` 交本轮已有结论，不要调用其他工具，不要继续分析」。

## D3 为什么回合结论仍是 failed

它确实没跑完：没有完成用户要的巡视/交付。把结论改成 ok 等于用一句「补交报数」冒充一整轮工作，是最坏的那种谎。所以：`ok:false` + `detail.wrapUp = { ok, chars }`——**失败但不再零数据**。

## D4 四个排除条件都是实测出来的

- **已有文本产出**：那段文本就是本回合的答案，再发一条 prompt 可能覆盖/冲淡它的意思。
- **非舰队任务**：普通定时任务没有报数工具面，问也问不出东西。
- **运行时中断**（重启/中止）：那不是回合的错，且子会话可能已经不在了。
- **压缩未达阈值**：一次压缩是正常现象（长回合常见），只有反复压缩才是「放不下」。

判据抽成 `shouldSalvageReport(detail, { interrupted, isFleet })` 纯函数，四条各有测试——因为整条 runner 驱动在单测里难以复现（超时预算由任务解析决定）。

## D5 为什么阈值是 2 次

实测的间隔是每次压缩 15–49s；两次已经吃掉半分钟到一分半，且这批回合的 `steps` 只有 5–38（不是在做几十步实活）。阈值只影响「怎么命名 + 是否补收尾」，不影响「何时停」——所以它不需要精确，只需要保守。

## Risks

- R1 误判：一次压缩 + 超时 → 不触发（阈值 2）。两次压缩 + 有产出 → 不触发。都排掉了。
- R2 收尾本身超时：90s 独立预算，失败即吞掉，原失败仍是结论（测试 4）。
- R3 与重试链的交互：收尾发生在 catch 内、单次 attempt 之后；不参与候选模型重试（那条链路只对上游快速失败生效）。
- R4 队列占用：收尾最多再加 90s，但换回的是本轮的报数——比让下一个节奏回合从零开始更省。
