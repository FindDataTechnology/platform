## Context

现有 `server/bots/wecom.js` 是自建应用适配器，已具备：AES-256-CBC 解密（`decrypt`）、sha1 签名校验（`signature`/`checkSignature`）、`tokenFor` 的 `{cred, cache}` 凭据轮换安全形态、`sendText` 的 `message/send` 成员单发。它的 `parseMessage` 直接取 `FromUserName` 作为 `chatKey`——这在单聊里正确，在群里会把"发言人"当成"会话"，同一个群里多人发言会被拆成多个互不相干的会话。

bot 车道的其余部分与平台无关：`handleMessage` 的守卫（长度/限流/工具姿态）、`collectTurn`（含 ask 拦截与超时暂停）、`runTurn`（流式标记、推理剥离、回复留痕）都不需要为群聊改动，只要 `chatKey` 语义正确。

本班刚修的两个事实已进入 spec 的 MODIFIED 段，实现上已存在（`reply()` 留痕、`routes/bots.js` 的 bootBuffer 重放），design 只需说明它们与群聊共存即可。

## Goals / Non-Goals

**Goals:**
- 群聊与单聊共用一条入站管线，只在**三处**分叉：`chatKey` 取值、提及剥离、回复通道。
- 新增类型不改动现有 `wecom` 自建应用的任何可观测行为。
- 群聊的会话模型零新增：继续用 `bot-<botId>-<sha1(chatKey)[:16]>`。

**Non-Goals:**
- 不做「监听整群」（平台不提供，也未申请该能力）。
- 不做群管理类能力（建群/改群/拉人）——`appchat/*` 只作为回复回落通道使用。
- 不做群机器人 Webhook（出站推送）接入：它与本需求的入站方向相反，混进来只会让人误以为能收消息。
- 不改 `social-bot-channels` 既有的会话派生、守卫、管理面结构。

## Decisions

**D1：新类型 `wecom-bot`，而不是给 `wecom` 加参数。**
两者回调报文形状不同（`chattype`/`chatid`/`response_url` vs `AgentID`/`FromUserName`），回复 API 也不同。用类型区分让 `adapterForBot` 的分派、凭据校验、管理面字段声明都保持"一类型一形状"，避免一个适配器里塞两套报文分支而让 `verifyWebhook` 的信任边界变模糊。备选（同类型加 `mode` 字段）会让每次改动都要判断"当前是哪种模式"，是同类分支膨胀的起点。

**D2：`chatKey` = 群 `chatid`（group）/ 成员标识（single），且由适配器决定，管线不知情。**
会话派生、限流桶、ask 拦截全部以 `chatKey` 为单位，因此只要适配器给出正确语义，上层无需任何改动。备选（在 `bots.js` 里按类型特判 `chatKey`）会把平台知识泄漏进平台无关的管线。

**D3：回复通道优先被动回复（`response_url`），超时后回落群发。**
被动回复绑定在该次回调的上下文里，天然只回给问话的群，且不依赖 `appchat` 的企业侧限制。但被动回复有窗口（官方口径约 6 分钟，agent 回合可能更长），窗口外的回复必须走群发通道，否则回复静默消失。回落通道失败必须**如实报错并留日志**，不得当作成功。

**D4：提及剥离放在适配器内，用"去掉前导 @ 段"而非正则匹配机器人名。**
机器人名可被管理员改名，写死名字会在改名后失效。按平台给出的提及标记结构剥离（并 trim），只 @ 不说话则产生空正文 → 交给既有空消息丢弃分支（已有日志），不新增路径。

**D5：先抓真实报文，再定字段映射。**
官方文档未说明智能机器人是否与自建应用共用同一回调 URL，且报文字段名细节分散在多篇页面。设计上把"第一次真实回调抓取"作为实现的**前置闸**：在拿到真实报文前不写死 XML 字段名，避免用自建应用的结构臆测。

## Risks / Trade-offs

- [智能机器人回调报文与文档不完全一致，字段映射写错导致静默不回复] → D5 的前置闸：先用真实报文校准，且实现第一条断言就是"解析出一条带 chatid 的群消息"。
- [被动回复窗口（约 6 分钟）短于长回合，回复回落群发时可能因企业权限失败] → 回落失败必须有明确日志与可判读错误；接受"回复失败"这一诚实结局，绝不静默。是否要在窗口将尽时改为先回执再异步补发，属于可后置的产品选择，先记入 Open Questions。
- [群里多人可见，工具姿态若被开启会把工具输出扩散到群] → 沿用全局 `BOTS_ALLOW_TOOLS`，不为群聊提供更宽松的开关；群聊不新增任何放宽通道。
- [新类型让管理面出现两个"企业微信"图标，运营者可能选错] → 管理面文案必须写清"智能机器人（群聊/单聊）"与"自建应用（单聊）"的能力差异，而不是都叫企业微信。
- [企业侧前置配置（建机器人、登记回调、可信 IP）不在代码控制内，可能与上线节奏脱节] → tasks 里把企微后台配置列为独立的前置任务，不通过则整个变更停在"代码就绪、未接通"的诚实状态。

## Migration Plan

1. 代码与单测先行（适配器 + 分流 + 提及剥离 + 回复通道选择），全部用构造报文验证，不依赖真实回调。
2. 企微后台创建智能机器人 → 用**真实回调**校准字段映射（D5 闸）→ 补齐/修正解析。
3. 单个内部群灰度：一人 @、多人 @、跨群、私聊并存四种情形各验一次。
4. 回滚：新类型是**新增**的，删除该 bot 配置即完全回退，不影响既有的 `wecom` 自建应用通道。

## Open Questions

- 长回合超过被动回复窗口时，是否需要在窗口将尽时先回一句"正在处理"再异步补发最终答案？这改变用户可观测体验，但不影响 spec 的行为契约（回复要么送达要么如实失败），可上线后再定。
- 群聊是否要支持把回复按 `markdown` 发送（企微群内渲染更友好）？属于呈现层选择，先按纯文本上线。
