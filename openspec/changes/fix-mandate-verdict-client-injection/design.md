## Context

对外披露闸的裁决是一次跨进程调用：runner（跑回合、准备对外文本）向 cell（持有委托状、判例、披露范围）取裁决。两个进程之间只有一条 HTTP 通道，部署时靠两个 env 拼出来。

打补丁前，这条通道在 runner 侧是断的——`mandateVerdictClient` 从未传入。本 change 把它接上，并把「接不上时算什么」的口径从隐性约定变成规格条文。

## Goals / Non-Goals

- **Goal**：通道可用时真做裁决；通道不可用时保持打补丁前的行为，一字不差。
- **Goal**：让「通道没配」与「通道拒了」在账上可分，堵掉「一律不发」冒充「闸门有效」。
- **Non-Goal**：不改 gateway。裁决端点走 runner 直连（部署侧给 URL），不给 gateway 开豁免口子。
- **Non-Goal**：不在 runner 侧缓存委托状副本。D8 已经否决过，理由（缓存过期窗口＝越权窗口）不变。

## D1 · 两个 env 缺一即不注入（而不是「有 token 就试」）

**问题**：部署会漏配。只配 `MANDATE_VERDICT_TOKEN` 不配 URL，或者反过来，都可能发生。这时有两种做法：拿半套配置硬试，或者干脆不注入。

**裁决：缺一即不注入。**

- **理由一（更严的一侧）**：半套配置硬试的失败形状是「每次对外应答都发一次 HTTP 到空/错的地址，拿到失败，于是拒绝」——行为上等于失败关闭，但它**每回合付一次网络代价**，而且把「部署配错了」伪装成「闸门在正常工作」。不注入则当场退回 `no_verdict_client`，一个本地常量，零网络。
- **理由二（可验证）**：不注入是**可判定的**——`typeof client !== "function"`，单测能覆盖，四个 env 组合都能枚举。半套硬试的失败面取决于 DNS、TLS、超时，验不全。
- **否决**：`URL` 有值、`token` 为空时注入一个必然 401 的客户端。401 与「未配置」在 `action_audit` 里都会落到 `ok:false`，读面分不开，等于把配置错写成了裁决结论。

**用户可见后果**：只配一半的部署，闸门读数与打补丁前完全一致。这条是**故意**的——它保证上产不会因为漏一个 env 就悄悄改变对外行为。

## D2 · 非 2xx 一律 `ok:false`（而不是「只有 5xx 才拒绝」）

**问题**：裁决端点会回 503（未配置）、401/403（错 token 或越权）、5xx（库挂了）、4xx（请求形状错）。UX 上容易想「只有服务端挂了算拒绝，403 是配置问题、可以放过」。

**裁决：任何非 2xx 都是 `ok:false`，任何异常、超时、非对象响应也都 `ok:false`。**

- **理由**：这是一条授权通道。授权通道的**唯一**肯定答复是「对端明确说 yes」。把 403 解释成「配置问题所以放行」，等于让「谁能改配置」变成「谁能绕过披露闸」——权限模型被降级成配置模型。
- **理由（可验证）**：`r.ok === false` 是单一判据，与服务端 `res.status(503)` 分支一一对应；而「哪些状态码算拒绝」是一张会随上游改动漂移的白名单。
- **超时 5s**：与 cell 侧其它同步调用同量级。超时即 `abort`，落到同一条 `ok:false` 分支，不挂在网上等。
- **响应形状**：`j.ok === true` 才放行——不是 truthy 判断。`"true"`、`1`、缺字段都不算肯定答复，落 `ok:false`。

## D3 · 失败关闭不改语义，只补可观测（否决「顺手加放行兜底」）

失败关闭把「闸门坏了」与「闸门拒了」压成同一个 `ok:false`。有人会想加一条「连续 N 次 no_verdict_client 就降级为 draft 放行」的兜底——**否决**。那等于定义了一个「用故障次数换授权」的口子，且故障计数是进程内状态，滚版即清零（本项目已有同类教训：进程内计数器每次滚版清零，会把证据擦掉）。

正解是把两者在**数据层**分开：`reason` 字段区分 `no_verdict_client` / `verdict_http_503` / `verdict_error: ...` / `bad_verdict`。规格要求可观测面上可分，实现上靠这个字段。

## 部署顺序（为什么它必须后于密钥）

1. cell 侧先配 `MANDATE_VERDICT_TOKEN`（否则端点恒 503，runner 注入后也只是把 `no_verdict_client` 换成 `verdict_http_503`——零功能变化、纯噪声）；
2. runner 侧再同时配 URL + token；
3. 观察第一行非空 `action_audit.mandate_domain`，才算通道真的通了。

顺序反了不会破安全（两种顺序都是失败关闭），但会浪费一次排障——读数从 `no_verdict_client` 变成 `verdict_http_503` 看着像变坏了，其实只是走到了下一道门。

## Risks

- **风险**：runner 注入后，若 cell 侧端点常年 503，对外车道会持续拒绝，且每回合多一次 5s 上限的调用。**缓解**：部署顺序（先配 cell 侧）+ `reason` 可分；5s 是硬上限，不无限等。
- **风险**：`MANDATE_VERDICT_TOKEN` 与 cell 侧不一致。**缓解**：`verdict_http_401` 是独立 reason，一眼可辨。
