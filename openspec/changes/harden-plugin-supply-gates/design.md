## Context

见 `proposal.md — Why`。三条实现边界来自现状：

- **合成是"读文件—过滤—追加—写盘"**：`writeLlmProfile`（`dsh-profile.js:303`）读 `cordis.patch.yml`，过滤掉 `id` 为 `llm-pi-ai` / `spill-policy` 的行，再追加平台自己的两行。它保证了"我们自己那两行唯一"，**没有**保证"没有别的行"。断言必须落在合成产物上，而不是落在写入动作上——否则只能管住一个入口。
- **工具面已经是"派生不物化"**：`deriveFullModeToolScope` 从 `installed_packs` 快照派生，`capByOperatorFace` 是最后一步的求交，且 `null` 表示"无过滤"。插件工具要进同一个 `presentServers` 与同一张派生表，而不是走第二条通道。
- **凭据面的既有事实**：relay token 由 `lib/scoped-relay-token.js` 派生、经 `credentialDelivery` 在回合边界注入；平台自己的凭据从不写进 bundle 声明。所以"声明里出现这些键名"本身就是异常信号，可作为出片期硬门。

## Goals / Non-Goals

**Goals**

- 三条断言都能被**注入用例**证明会红（先证明能红，再证明默认为绿）。
- 断言实现单一：写盘前与启动前调同一个函数，不允许两份判定。
- 拒绝信息可归因到"哪一行 / 哪个 bundle / 哪一类越界"。

**Non-Goals**

- 不做进程级沙箱（Node 同进程内做不了真正的隔离，假装有会更糟）。
- 不改 dsh 上游的插件模型，也不 fork 它的加载器。
- 不引入"插件自述可信"的任何新机制：类别声明是我们这边供给白名单的字段，不是 bundle 自己的声明。

## Decisions

**D1. 断言对象是"合成后的行集合"，不是"写入者的行为"。**
替代方案：在 `writeLlmProfile` 里多过滤几个 id。否决理由——只封一个写入口，bundle 层贡献的行仍然进得去；而合成产物是唯一事实。断言纯函数化（输入 rows → 违规清单），便于单测与复用。

**D2. 判定"会注册模型路由"用形态匹配而不是 id 白名单。**
理由：id 可以随便起，`name` 才是包身份。判定应同时看 `name` 是否命中模型/提供方形态（`dsh-llm*`、`llm-*`、`*provider*`），以及 `config` 里是否出现 `providers` 或 `baseURL` 形态。白名单只能作为补充，不能作为唯一判据（否则改个 id 就绕过）。

**D3. 插件工具通过"服务名参与同一次派生"接入，不新增裁剪通道。**
理由：第二条通道必然与第一条漂移，而工具面是安全面。实现上把插件贡献的服务名并入 `presentServers`，并让席位声明的解析对插件服务与 MCP server 一视同仁。

**D3'. 实施时的发现：插件原生工具无法被现有工具面约束，因此 v1 禁止 bundle 贡献工具。**
设计原打算"把插件贡献的服务名并入 `presentServers`"。实测：`dsh-profile.js:1481` 的 `capByOperatorFace(scope.mcpTools, Object.keys(servers))` 里 `servers` 只来自 mcp.json ——**平台唯一的工具闸是按 MCP server 名索引的**，而插件原生注册的工具没有 server 键，`plugins/list`（`dsh-profile-template/platform-plugin-supply-bridge.js`）也只报 bundle 级 name/version/enabled，不报工具名。所以"并入"没有数据源，硬接一条只会得到一个看起来在管、实际管不到的假接缝。
口径收紧为：供给白名单的 `contributes[]` 允许 `skill` / `ui` / `service`；`tool` 与 `llm` / `credential` / `channel` 一起列入禁止集。想开放 `tool`，前提是先有一条能按名字判定的闸（例如 dsh 暴露工具清单 RPC 后做"声明即白名单 + 其余默认拒"）。

**D4. 凭据键检查放在出片期（构建时），不放在运行期。**
理由：运行期检查只能"发现已经装进来了"，构建期检查能"不让它进"。运行期那侧只保留"绝不把平台凭据注入 bundle 作用域"这一条既有事实。

**D5. 失败姿态是 fail closed：拒绝启动，不降级。**
理由：`agent-fleet-cockpit` 那种"缺数据显示空态"的诚实降级适用于读面；启动期的越界是安全事件，降级会让"启动成功"变成假绿灯。

## Risks / Trade-offs

- **[误杀：某个合法的第三方插件名字里带 llm]** → 形态匹配先用"`name` 在模型域 + `config` 有 providers/baseURL"两条件与，再给运营者一个**显式例外白名单**（带台账记录与到期日）。宁可偶尔人工放行，也不默认放行。
- **[断言在热路径上拖慢启动]** → 断言是纯函数、行数量级在几十，成本可忽略；只在启动与写盘各一次。
- **[插件工具入派生后与既有 pack 工具面语义打架]** → 交集语义沿用 `capByOperatorFace` 的既有三条（无过滤则 face 即过滤、有 allowlist 求交、空集显式为空），不新增第四条。
- **[出片期凭据扫描误报]** → 扫描只匹配**键名集合**（不是内容、不是宽泛的 `*TOKEN*`），键名表集中一处维护，误报靠加注释而非放宽匹配。
- **[例外白名单变成后门]** → 每个例外必须带到期日，过期自动失效并要求复审（与"安全单行道"纪律同族）。

## Migration Plan

1. 先落纯函数断言 + 单测（不动启动路径）：此时断言可被单独运行。
2. 接启动路径：先以"只记录不阻断"跑一轮（观察真实部署里有没有违规），再切 fail closed。
3. 工具面接入与凭据扫描：`presentServers` 扩源、出片脚本加检查。
4. 回滚：断言可改为只记录（一个开关）；凭据扫描可摘；工具面扩源回退到只含 MCP server。三者互不依赖。

## Open Questions

- 显式例外白名单是否需要 UI（当前设计为文件 + 台账，够用再说）。
- 插件自起渠道进程的检测手段（进程树 / 端口监听）在这一版只做"声明类别 + 合成期拒绝"，运行期探测留到有真实需求时。
