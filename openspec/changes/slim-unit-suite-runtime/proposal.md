# slim-unit-suite-runtime

## Why

unit 套件在冷 2 核 runner 上实测 **63 分钟**（run 42630983629）。这个数字已经很危险：
作业上限 90 分钟时只剩 ~27 分钟给 build + e2e，一次慢就会被 job kill，而那种红在报告里
和"产品坏了"长得一模一样（2026-11-09 已因此误判两次，一次归咎于"资源饥饿"、
一次归咎于"某条用例悬挂"）。

**这不只是"慢"，它已经是门禁自身的吞吐上限**（2026-11-09 实测）：镜像仓的 concurrency
是 QUEUED（`queue-release-ci-runs`），而每次快照推送都排一次 unit。快照 `6f963a019`
的 CI 从 14:46:55Z 起跑，超过 60 分钟未完成，更新的 `ffc8168b0` 已经排在它后面。推送间隔
10–30 分钟 vs 单次 unit 60+ 分钟 ⇒ **CI 队列只增不减**，强制门禁反而积压。把作业上限抬到
120 分钟只够一次运行，治不了队列增长。

**`--test-timeout` 是"抓悬挂"不是"提速"，已实测**（2026-11-09，五条各睡 3 秒的用例）：

| 配置 | 总耗时 | 结果 |
|---|---|---|
| 无超时 | 15.33s | 5/5 通过 |
| `--test-timeout=1000` | **7.25s** | 五条**各 1 秒点名失败** |

即：它把**每条**用例压在 1 秒，但它是逐条上限、不是总时长上限。所以 63–81 分钟的步骤
不能归咎于"超时没生效"——是几百条用例各自合规地累加。180 秒对正常用例毫无约束力（只抓悬挂），
**能降总时长的唯一杠杆是条数与启动成本**。

**120 分钟也不够，且"卡住一条会堵死整条队列"，已实测**（2026-11-09）：快照 `ffc8186b0`
（带 `--test-timeout=180000` 与 `timeout-minutes: 120`）的 unit 从 16:04:49Z 起跑，
97 分钟仍未完成；同期三个更新的 run 全部 cancelled、最新的排成 pending。它最终会被 120
分钟砍掉——**而那一刀在报告里与"产品失败"长得一模一样**。所以当前状态下门禁不是"慢"，
而是**会周期性产出假红并堵住后续验证**。

**成因是集中的，不是普遍的**（初量，2026-11-09）：489 个测试文件里 **58 个**会起真实
server 或 dsh 子进程（`spawnTestServer` / `initTaskEngine` / `attachAgentSession`），
每个都付一次子进程启动。12% 的文件构成主要成本，所以"把 489 个文件平均切开"不是对症解法。

**上面这条初量在 2026-11-10 被更宽的扫描修正，并推翻了由它派生的两个解法**（重要）：

| 量 | 值 | 含义 |
|---|---|---|
| 含任何 `spawn` 形态的文件 | **73 / 510** | 比初量的 58 多（正则更宽，含裸 `spawn(`） |
| **落在 `test(...)` 体内的 spawn** | **26 次** | 几乎全部 spawn 是**模块级、每文件一次** |
| 空壳文件进程开销 | 5 文件串行 0.51s；单文件 0.15s ≈ **0.1 s/文件** | 511 文件全串行也只要 ~1 分钟 |

两条推论，直接改写下一轮该做什么：

1. **"每用例起一次服务，共享 fixture 能摊薄"是伪命题**。文件内的 spawn 早已在**文件级**
   只付一次（26 次散在 73 个文件里）；跨文件共享 fixture 不可能——node 每个测试文件是
   独立进程。所以"简化 boot"只能降**每文件**启动成本，摊薄不了。
2. **63 分钟不是进程启动成本**。0.1 s/文件 × 511 ≈ 1 分钟，剩下 ~62 分钟来自**每文件真实的
   import + 用例工作**（server.js / db.js / better-sqlite3 装载 + 真实库操作）。

**于是真正的容量杠杆是 `--test-concurrency=1` 的作用域**：它由 `1e3ffc509` 引入，
commit 理由是"串行化消并发竞态（614/614 两连绿）"——为了压掉**一个从未点名的子集**的竞态，
把**全部文件**一起串了。若那个子集只占少数，其余文件并行即可把 62 分钟压到个位数。
"哪些文件真的需要串行"至今无人量过；注意它与"谁慢"是两个问题——
**per-file 耗时榜单只答"谁慢"，答不了"谁能并行"**。

**并发 8 的两组对照实验（2026-11-10 本机实跑，真实依赖）**：

| 样本 | 串行 | 并发 8 | 失败集 |
|---|---|---|---|
| 24 个静态隔离文件（mkdtemp 根、无 spawn、无写死路径） | 20s | **7s（2.9×）** | 两侧同为 3 条既有红，逐条同名 |
| 24 个 spawn 重文件（无写死路径） | 27s，131/131 | **9s**，131/131（修后） | 修前 1 红 = `test-queue-supersede` 的 teardown 竞态 |

两条结论：

1. **并发本身不引入不稳定**——隔离样本的失败集与串行**完全相同**（3 条为既有的 empty-turn /
   scoped-registration，与本议题无关）。
2. **唯一那条"并发才红"是潜伏的真缺陷，不是并发**：`test-queue-supersede` 单跑 3 次也会挂
   1 次，根因是 `lib/persistence.js` 的 flush 在目录被 teardown 删掉后抛 ENOENT 逃逸成
   `unhandledRejection`（已单独立单修复并归档：
   `2026-11-10-fix-persistence-flush-teardown-race`）。修后同一并发跑 131/131 全绿。

**静态排查也支持"串行可以缩"**：499 个测试文件里**没有一个**写死端口（全部 `listen(0)`）；
241 个文件改 `process.env`、25 个 `process.chdir`——但每个测试文件是**独立 node 进程**，
env 与 cwd 都是进程内的，**跨文件不可能争用**。真正的争用通道只有：写死的 `/tmp/...`（12 个）、
`~/.dsh`/`os.homedir()`（5 个）这类**共享路径**。也就是说"必须串行"的名单应当是十几到几十个
**点名文件**，而不是全部 499 个。

**120 文件大批量（2026-11-10）**：串行 3276 s / 30 条红，并发 8 **528 s / 29 条红**（6.2×）。
两个时间都要打折（串行那次与后台诊断抢 CPU），可信的是 24 文件那两组干净对照；这批的价值是
**失败集**：25 条两边同红、5 条只在串行红（本身 flaky）、**4 条只在并发红且全在同一个文件**。
那 4 条经查**不是并发造成的**——单跑也红，抛的是 `ReferenceError: options is not defined`
（`agent-runner/manager.js:1005`），是 rebase 期间合进来的 `1ac6bb6c5` 读了一个 `turn()`
从未有的参数，**每个完成的回合都会抛**（已单独立单修复）。

**方法论教训（写进这里免得下一轮再踩）**：对照组必须跑在**同一棵树**上。跨 rebase 比失败集，
差集里会混进"新合进来的提交"，既可能把真 bug 误记到被测变量头上（这次差点），也可能像这次
一样反而靠差集把真 bug 抓出来（赚了，但纯属运气）。

**三条既得事实（本轮实测，避免下一轮重新发现）**：

1. **`--test-shard` 不能用**。它切的是**扁平化的用例列表**，不是文件列表：四个文件时
   shard 1/2 里同时出现 `browser-lane-artifacts` 与 `queue-health` 的用例。同一文件的用例
   会落到不同 runner **并发跑**，而 `--test-concurrency=1` 存在的理由正是文件内顺序依赖
   （queue-health 的"遗留 queued 记录不泄漏"只有在前面的用例先跑过才有意义）。
   已用断言钉住（`scripts/test-unit-shard-safety.mjs`）：`test:unit` 不得出现 `--test-shard`。
2. **停摆形态与"悬挂"不同**。一处早期判断（"某条用例卡死"）已被推翻：`--test-timeout=180000`
   确实生效，63 分钟是**大量慢用例累加**，不是单条无限等。
3. **缩容先量**。node 的 reporter 不带文件名（TAP 顶层 subtest 是单条用例），所以
   per-file 榜单只能逐进程计——工具已就位：`scripts/profile-unit.mjs`
   （默认自动挑那 58 个 spawn 重的文件；带两道前置检查，拒绝在无依赖或软链依赖的树上跑）。

## What Changes

本轮**只立契约不改造**——把问题、真因、已排除解法、量尺写进台账，让下一轮照数据动手，
而不是重新摸索一遍。

## Capabilities

（无 —— 本单不改变任何产品行为，纯工程性能议题。）

## 非目标

- **不改 CI 拓扑**：作业上限已由 90 提到 120 分钟作为止损（`a4f162950`），够用一阵。
- **不动 `--test-shard`**：已证不可用，理由见上并已入闸。
- **不裁用例**：没量出谁是慢源之前不动刀——`profile-unit.mjs` 就是为此准备的。
- **不重构 spawn 套件**：那是本单的后续工作，需要先有 per-file 榜单。
- **不为摊薄而建共享 server fixture**：已证伪——spawn 是每文件一次，跨文件共享做不到
  （见上）。

## 后续（本单不执行）

1. 在**有真实依赖**的主树跑 `node scripts/profile-unit.mjs`，拿 per-file 耗时榜单。
   注意：`paas-dualcred-26b1a3` 工作树的 `node_modules` 是**软链**到主树，按设计会被
   该脚本直接拒绝（共享 sqlite 锁会把问题伪装成产品红）。
2. 另量一件事——**串行的作用域**：把 `--test-concurrency` 从 1 抬到 N，逐批找出实际会红的
   文件，把"必须串行"收缩成一张点名清单。这才是能压 62 → 个位数分钟的杠杆；耗时榜单
   只答"谁慢"，答不了这个。
3. 按榜单与点名清单决定：最慢的几个简化 boot / 必须串行的收缩成显式白名单 / 移到独立 CI 车道。
   若最终要分片，必须**自己按 `ls scripts/test-*.mjs` 切文件列表**，并加断言
   「已执行文件并集 == 全集」——绝不能用 `--test-shard`。
