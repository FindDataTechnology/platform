## Context

见 `proposal.md - Why`。三个数决定了整个形状：`server/routes/voice.js:25-26` 的
`MAX_UPLOAD_BYTES = 25MB` 与 `ASR_TIMEOUT_MS = 120_000`，以及转发时写死的
`response_format=json`（只回 `text`，不回分段时间）。一小时 64kbps 音频约 28MB，三项全撞。

另两条既有事实：上游（豆包/腾讯）在词元侧本来就是**异步任务**（submit + poll，见
`openspec/changes/archive/2026-10-22-audio-lane-multi-upstream/design.md`），所以「一次长请求」
在协议层也不成立；而房间已经有 `human | agent | system | event` 四类消息行，会议纪要天然落在
`system|event` 道，不需要新消息类型。

## Goals / Non-Goals

**Goals:**

- 长音频能进来，且**边传边出**：前 20 分钟的文字不必等整场录完。
- 单片失败只影响那一片，能单独重试。
- 归并可离线验证：纯函数、确定性、可对照。
- 音频转写完即删，只留文本。

**Non-Goals:**

- 不做说话人分离与身份归属（`add-speaker-attribution`）。
- 不做实时字幕（低延迟逐字上屏）；本件的「实时」是「已完成的片可读」。
- 不做断点续传的跨设备迁移（同一采集只对发起人开放）。
- 不改 `voice-lane` 既有端点与 25MB 上限。

## Decisions

### D1 — 分片上传，不是「整段交给上游异步任务」

**决定**：客户端按固定时长切片（默认 30s，可配），逐片上传，服务端逐片转写。

**理由**：整段异步任务要求平台侧实现两套上游异步协议（豆包 WebSocket 双向流、腾讯云 TC3 签名 +
异步任务），且**失败无法局部重试**——整段失败就得整段重来，一小时的音频白烧。分片让失败域被限制在
30 秒内，且已完成的片永远可读。

**否决的替代**：整段提交 + 轮询。否决理由：失败域太大、无局部可用性、且要新增协议适配。

### D2 — 时间轴用「片起始偏移」，不用上游时间戳

**决定**：每片记录 `start_ms = seq × chunk_ms`（客户端上报实际值，服务端校验单调），归并按它排序；
段文本只用这一层时间，不编造字级时间。

**理由**：当前转写协议不回时间戳，硬凑精度就是编造。片级偏移是**真实知道**的那一层，精确到 30 秒，
足够阅读、足够后续归属（归属按片粒度做，正合适）。

### D3 — 归并是纯函数，输入是「有序的 (offset, text)」，输出是段列表

**决定**：`mergeChunks([{seq, startMs, text}]) → {segments: [{startMs, text}], fullText}`。
空文本片跳过；边界不做事后拼接，靠「片内文本已完整」这一前提（切点由客户端保证在静默处，切不准的
损失由人工订正承接）。

**理由**：跨片拼接需要一个「智能」的接缝判断（句尾/句首），而任何接缝算法都会在某个语言/某种语速上
出错，且难以测试。承认「切点可能切开一句话」，用**订正**兜底，边界更诚实：宁可让人改一次，不要让
算法悄悄改。

### D4 — 幂等用 (capture_id, seq) 唯一约束，不是内存去重

**决定**：`voice_capture_chunks` 上 `UNIQUE(capture_id, seq)`；重复上传走「已存在则返回既有状态」，
不重复转写、不重复计费。

**理由**：移动网络必然重传。内存去重跨进程失效（`docs/memory` 里「重启冒充修复」的教训同族）。

### D5 — 预算双闸：分钟数在服务端累计，金额从既有 usage 派生

**决定**：分钟数按「已成功片的时长之和」累计；金额取既有 usage 记录的聚合。任一触顶即停止新片转写，
但**继续接收**分片（暂存），使「解开上限后可补转」。

**理由**：直接拒绝分片会让用户丢音频；暂存 + 补转是更好的失败模式。代价是暂存要占空间 → 暂存有
自己的保留期，超期即删。

### D6 — 音频不留存：转写成功即删，配置项可改

**决定**：默认 `retainAudioMs = 0`（转写成功即删）。删除与「片完成」写在**同一条 UPDATE** 里
（`status='done'` 与 `audio=NULL` 原子生效），因此删除本身没有独立的失败分支可进重试队列。

**理由**：会议录音是高敏内容，默认不留是唯一站得住的默认。留存可配是给「需要回听」的客户开的门，
不是给默认开的。

**实现订正（4.3 落地时）**：初稿写的是「删除失败进重试队列」。落地发现真正会卡住的是另一种情形——
进程在上游返回与落库之间死掉，分片停在 `transcribing`，`beginChunk` 会永远以「忙」拒绝它，
那一片就永久不可重试。所以「重试队列」改成**归还卡住的分片**：`transcribing_at` 超过 10 分钟的分片
由清理任务置回 `failed`（`error_code='stale_transcribing'`）并保留音频，重试一次请求即可补齐；
`retainAudioMs>0` 的音频仍由同一清理任务按各自窗口删除。

### D7 — 入房走 event 道，不伪装成人工消息

**决定**：归并文本入房时落 `kind=event`（或 `system`），`meta.source="capture"`，归属标注为采集标识 +
发起人（onBehalfOf 语义复用）。不计入回合配额与熔断（沿用 team event 行的既有纪律）。

**理由**：伪装成人类消息会污染成员归因与计费口径，且会触发回合路由（一条会议纪要唤醒所有 agent 是
灾难）。

## Risks / Trade-offs

- **[切点切句]** → 承认并给订正；订正留痕；不做接缝算法。
- **[暂存占空间]** → 暂存有保留期（默认 24h），超期删；配额触顶时提示「暂存将于 N 小时后过期」。
- **[单片重试放大成本]** → 重试有次数上限（默认 2 次），且每次重试单独计费可查。
- **[三端上传语义不一致]** → 分片回调收进 `add-voice-input-mobile` 的录音适配器，三端共用同一个
  「切片 + 补偿重传」实现，不允许每端自己写重传。
- **[老库无表]** → 两表 `CREATE TABLE IF NOT EXISTS`；采集端点未配置时 `voice_not_configured`。

## Migration Plan

1. 建两表（采集会话、分片），空表即行为不变。
2. 抽出 `server/routes/voice.js` 里的转发逻辑为可复用函数（**对外契约零改**，回归用例钉住）。
3. 上线采集端点（web 先接），预算与留存取默认。
4. 三端接入分片回调。
5. 回滚：下采集端点即回到今天；两表留着无害；预留音频按清理任务自然过期。

## Open Questions

- 分片时长默认值（30s）与最小/最大值，需按上游超时（120s）与弱网实测调；spec 不写死数值。
- 归并后是否允许「按分钟分页阅读」：本期一次给全文（会议通常 < 2 小时，全文可承受）；
  超过阈值再分页，形态随 `add-zhiyu-mobile-clients` 一起定。
