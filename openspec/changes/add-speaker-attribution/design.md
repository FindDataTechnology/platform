## Context

见 proposal.md — Why。技术现状（决定实现形状的四件事）：

1. **转写是纯代理，且只读一个字段**。`server/routes/voice.js` 把上传原样转发到
   `${apiBase()}/v1/audio/transcriptions`，请求里写死 `response_format: "json"`，响应里只取
   `payload.text`（`const text = typeof payload?.text === "string" ? payload.text : ""`）。
   所以**今天即使上游给了分段说话人，也在这一层被丢掉**——这是本件唯一的硬阻塞点。
2. **路由消费侧已经存在**。`gateway/zhiyu/voice-router.js` 是纯函数（无 DB / 无时钟）：优先级
   `mention > attribution > intent`，`ATTRIBUTION_CERTAIN = ["session","bound"]`，
   短路规则（1.2）与"不猜"规则（2.4，`anonymous` 落 `needs_confirmation`）都已实现并有测试。
   本件**不需要重写路由**，只需要开始有人填 `attribution`。
3. **采集链路的产物是一行文本**。`add-voice-capture-lane` 的分片→逐片转写→按偏移归并，产出
   「一条按时间排列的文本线」，入房与导出都消费它。
4. **声纹不可用也不能用**。既有裁决：声纹永不作为认证因子（L3）；本件把它延伸为
   声纹也永不参与身份判定——只有显式声明与席位绑定两个来源。

## Goals / Non-Goals

**Goals:**
- 让转写结果**可以**带分段说话人标签，并在拿不到时逐字节退回今天的行为。
- 让归并产物以分段携带说话人，同时导出/入房文本仍可直读。
- 提供一条**可审计**的归属链：谁基于什么被认定成谁，确定性等级是什么。
- 把归属接进既有 `attribution` 信号，让「按人路由」在消费侧零改动地生效。

**Non-Goals:**
- 不做声纹注册/比对，不做跨会话的说话人记忆（本件只在本场有效）。
- 不重写 `voice-router` 的优先级模型；不动 `mention` 与 `intent` 两条路径。
- 不做实时流式说话人分离（整段/分片批处理即可）。
- 不改转写的 25 MB 上限与凭据通路。

## Decisions

### D1 — 分段开关按请求走，默认关，响应形状向后兼容

`POST /api/voice/transcriptions` 增加一个可选的请求字段（multipart 里的
`diarize=1` 或等价开关），开启时向上一跳请求能带分段的响应形状（`response_format` 由
`json` 换成上游支持分段的那个值，例如 `verbose_json`，具体值以实现时的实测为准），
并把 `segments[]`（`{start, end, speaker, text}` 的规范化形状）附在响应里。

**为什么不是"总是请求分段"**：上游对分段的实现差异大，且旧调用方（Composer 语音输入）只需要
`{text}`。默认开会把一个纯文本消费者拖进未知字段的兼容问题里，也违反「不改输入框语音行为」。
**替代方案**：加第二个端点 `/api/voice/transcriptions/diarized` —— 被否，同一份凭据/超时/上限
会分叉成两份实现。

### D2 — 规范化落在服务端，不把上游形状泄给调用方

上游可能是 OpenAI `verbose_json`，也可能是词元侧自己的分段字段。服务端 SHALL 归一到
`{ text, segments: [{ startMs, endMs, speaker, text }], degraded?: {reason} }`，其中
`speaker` 是**上游标识**（字符串/序号），不是人名。调用方只认这一个形状。

**为什么**：跨渠道形状漂移是本仓反复踩过的坑；只暴露一个形状，才有"一处归一、处处一致"。

### D3 — 降级是显式的数据，不是隐式的空

拿不到分段 → `segments` 退化为一段 `{ speaker: UNKNOWN, startMs: 0, endMs: 总时长 }`，
并置 `degraded.reason`（`upstream_no_diarization` / `upstream_malformed_segments`）。
MUST NOT 返回空数组，也 MUST NOT 编造 `说话人 1/2`。

**为什么**：空数组会让下游把"没标签"和"没人说话"混为一谈；编造标签会让归属链失去可信度，
而这正是本件要建立的唯一资产。

### D4 — 归属是「证据 → 等级」的函数，不是相似度打分

归属输入只有三类证据：`self_declaration`（本场声明/入会选定）、`seat_binding`（席位已绑定主人）、
`none`。输出等级映射固定：

| 证据 | 等级 | 可否走默认接收方 |
|---|---|---|
| 本场声明 | `session` | 可以 |
| 席位绑定 | `bound` | 可以 |
| 无证据 | `anonymous` | 不可以（落 `needs_confirmation`） |

本件**不引入 `inferred` 的证据来源**（相似度/上下文推测一律不做）。proposal 里保留了
`inferred` 这个等级名，是为了让未来若出现新的合法证据时有位置可放，而不是现在就开一条
"猜"的路。**这条要写进代码注释，否则下一个人会以为留了接口就该用**。

**为什么**：`ATTRIBUTION_CERTAIN` 已经只认 `session`/`bound`——把"猜"加进来会静默改变
路由的默认行为，而默认行为的代价是私密对话被送给错的人。

### D5 — 声纹既不参与归属，也不参与认证

实现层不得调用任何声纹/音色比对服务；`speaker` 标识只是**本场内的聚类 id**，
跨场不保留、不入库为身份。API 响应里 MUST NOT 出现"该声音属于某人"的结论字段。

**理由**：既有裁决（声纹 L3 永不作为认证因子）的加强版——连"辅助判断"都不做，
因为一旦做了，它就会在下一次需求里被当成证据。

### D6 — 确认交互落在既有 `needs_confirmation`，不新增状态机

归属不确定时不新增"待归属"实体，而是复用 `voice-router` 已有的 `needs_confirmation` 结果：
候选项来自房间花名册（本场参与者），一次人工选择即完成投递。选择结果**不回写**归属模型
（不形成"上次张三选过"的记忆），只影响这一条消息。

**为什么**：一次性确认的成本是一分钟；把它变成学习型记忆，就等于用人的一次点击给未来所有
消息背书，而那份背书本件没有可信来源支撑。

### D7 — 数据模型：分段表加可空说话人列，空即旧行为

采集 session 的分段记录增加 `speaker`（可空）与规范化的 `startMs/endMs`。空值语义为「未知」，
与今天的渲染路径一致，因此无需回填、无迁移风险；导出与入房读同一列。

### D8 — 主路是「按流归属」，不是「从混音里分离」（附录 A 实测后的修正）

原设想是从一段混音里分出说话人。附录 A 证明词元侧今天**既无 diarization 也无分段**，
所以主路改为：**每一路采集流本身就是一个人**（各自设备、或房间里按席位分配的采集），
`speaker` 由**流的来源**直接给出。

**为什么这是更好的方案，而不只是退而求其次**：

- 它**没有推断成分**——"这段话来自李四的流"是事实，不是判断。D4 的证据表因此天然成立：
  流绑定到席位即 `bound`，本场声明即 `session`，两者都不需要模型。
- 它不需要上游任何新能力，今天就能交付完整价值。
- 它与「声纹永不参与」的纪律同向：证据是**谁上传的**，不是**听起来像谁**。

**代价与边界**：混录（一个房间一支麦）**得不到**按人归属。这种场景下归属只能是
`anonymous` → `needs_confirmation`（D6），这是正确的失败方式，而不是猜。若将来词元支持分段，
混录场景由附录 A 的探测放行、只改归一层，再叠加 diarization 作为额外证据源——但**分级仍按
D4**，diarization 只可能产生 `inferred`（需确认），不可能升到 `session`/`bound`。

**替代方案**：自建分离模型（whisperX/pyannote 类）。否决理由有三：一是与「不做声纹、不猜」
的纪律冲突（这类模型输出的就是概率归属）；二是本机/集群要多背一个 GPU 级依赖；三是它解决的
是一个「按流归属」已经能正确解决的产品问题。


## Risks / Trade-offs

- **[上游根本没有 diarization]** → 本件的价值兑现不了，但降级路径仍保证零回归；设计上把
  "能不能拿到标签"作为**第一件实测任务**（任务 1.1），拿不到就先停在降级形态、不硬上归属。
- **[上游分段与文本不一致（吞字/重字）]** → 归并按偏移对齐、以文本为准校对；发现不一致时
  记 `upstream_malformed_segments` 并退整段，而不是把错位的分段硬拼成文档。
- **[误把 `speaker` 当身份]** → 服务端把 `speaker` 与 `personId` 分成两个不同字段名，
  响应里不出现"这个人是谁"的推断；命名上杜绝误用。
- **[确认交互被滥用成打卡]** → 只在 `anonymous`/`inferred` 时出现；`session`/`bound` 不打扰人。
- **[性能]** 请求分段会让上游处理变慢，且分片多时响应更大 → 分段开关只用于会议录音归并
  （分片批处理），不用于输入框单句语音。

## Migration Plan

1. 先实测词元 ASR 是否支持分段（任务 1.1）——**已做，见附录 A：不支持**。
   因此主路径改为 D8 的「按流归属」，降级形态先行上线。
2. 服务端归一 + 降级（默认关），此时**行为零变化**，可独立上线。
3. 采集链路按读者绑定落 `speaker`（每路采集 = 一个说话人），导出/入房读同一份分段。
4. 归属：先只做 `seat_binding`（最容易验证、来源最硬），再放开 `session` 声明。
5. 回滚：关掉分段开关即回到今天；新增列可空，回滚不需要数据修复。
6. 词元侧将来若支持分段：只改归一层的「上游形状 → 我们的形状」，其余不动（附录 A 的
   探测脚本就是验收工具，届时重跑一次即可判定）。

## Open Questions

- 词元侧什么时候会上 diarization（本件不阻塞；附录 A 给了可重跑的判据）。
- 「入会时选定身份」落在哪个界面（房间成员行 vs 录音开始前的一次确认）。**已定**：
  走**录音开始前的一次性参与者确认**——它不碰房间花名册 UI（那份界面此刻有别的会话在改），
  且证据在音频之前就成立，归属因此是确定性的而不是事后补的。

## 附录 A · 上游能力实测（任务 1.1/1.2，2026-11-13）

**方法**：本机合成两段不同音色的中文语音（`say -v Tingting` / `say -v Meijia`，各一句），
按顺序拼接成 10.4 s 单声道 16 kHz mp3，直接打
`POST https://token.finddatatech.cloud/v1/audio/transcriptions`（凭据取部署的 `LLM_API_KEY`，
即语音车道的回落项；**合成音频，不含任何用户数据**）。

**读数**：

| `response_format` | HTTP | 响应顶层 keys | 结论 |
|---|---|---|---|
| `json` | 200 | `text` | 基线 |
| `verbose_json` | 200 | `text` | **静默忽略**：没有 `segments`、没有 `words`、没有时间戳 |
| `diarized_json` | 400 | `error` | 直接拒绝 |

转写质量本身没问题，两句话都被正确识别（48 字，顺序正确）。**但没有任何说话人信息，
连分段与时间戳都没有。**

**两个必须记住的教训**：

1. **`verbose_json` 是被静默忽略的，不是被支持的。** 返回 200 且形状退化成 `{text}`——所以
   「请求成功」绝不能当成「拿到了分段」。实现里判定"有没有分段"只看响应里**有没有
   `segments` 数组**，不看状态码、也不看我们请求了什么。（同族事故：向量车道 200 + 非 JSON
   被静默降级成关键词召回。）
2. **`diarized_json` 被 400 拒绝，说明车道对未知 `response_format` 是严格校验的。** 这意味着
   将来上游支持分段时，很可能是**换了一个新的合法 `response_format` 值**——届时探测脚本要
   挨个试候选值（附录里的脚本已经这么做），而不是假设 `verbose_json` 会升级语义。

**对本件的直接后果**：分成两半看。

- **说话人分离（本件原设想的主路）在词元侧今天不存在。** 任何"从一段混音里分出谁说了什么"
  的实现都只能自己上模型——那是另一个量级的事，且与「不做声纹、不猜」的纪律相冲突。
- **但「谁说的」仍然可以确定地知道**：如果每一路音频本来就是**一个人**在说（各自设备/各自
  席位上传），那么"谁"由**流的来源**给出，不需要任何分离算法。这条既不需要上游支持，也比
  diarization 更可信——它没有推断成分。见 D8。
