# 结算 v2：部署者分成走收益账，租金留在容量闸门后

M3 出口判据（两个不同用户的 agent 互相调用、完成结算）把「钱怎么分」逼到台前。v1 现状：外部调用者按价目表在边界被扣款（adjustBalance subtract，幂等键=usage id），部署者的部署键承担上游模型费，平台静默净得差额——部署者零参与、零激励。决策：①**分成=收入分成，不是毛利分成**：每笔真金扣款回合（settler=NULL 且调用者≠部署者）按 agent 价目 ×（1−平台抽成，默认 30%，纯配置旋钮）记入部署者收益账；成本波动（车道/缓存）不进入分成公式，规则简单可预期。②**记账与结算分层不变**：平台侧新增 `deployer_earnings` 账本（usage_id/deployer/agent/amount/status）为生意权威，与扣款同回合结算；入账复用 adjustBalance add，幂等键=`share:<usage_id>`；sub2api 仍然只管钱（ADR-0014「它管钱，不管生意」延伸到收入侧）。③**闭环抵扣，不提现**：v1 收益只抵部署者自身消耗（模型费/未来租金），余额语义从「预付消费」扩展为「消费+收益混合」，面板标注收益行；提现涉及合规主体与结算通道，显式延迟。④**负保护**：退款/失败回合不产生负分成，分成只对成功扣款行生成，逆差平台自担。⑤**host 与 share 互斥**：同一回合要么 host 通道（部署者额度付费=部署者是消费者）要么产生分成（部署者是供给者），永不叠加。⑥**租金不收，闸门照旧**：当前 6/500 agent 驻留，容量充裕，租金的存在意义是公地治理不是收入——500 上限触发后才启用「每 agent·日固定扣减（adjustBalance，幂等键=`rent:<agent>:<date>`），余额耗尽转 paused（draining 不删除），充值即恢复」。

## Considered Options

- 分成走 sub2api 虚拟用量端点（收入侧原生记账）：端点至今未落地，且把价目/抽成等生意规则塞进账本工具，重蹈 ADR-0014 否决过的耦合。否决——平台算分成，sub2api 只见 adjustBalance。
- 按毛利分成（扣款减上游成本后再分）：上游成本 C 对部署者不可见且随车道/缓存波动，对账解释成本远超激励价值。否决——收入分成，部署者「每被叫一次得多少」可预期。
- 租金现在就收：6/500 占用、无容量压力，供给侧正在培育期，收费只会抑制部署；租金的真实触发器是容量，不是收入目标。否决——留在闸门后。
- 提现随 v1 落地：合规主体、结算通道、税务全是独立工程。延迟——闭环抵扣先跑通激励。
- 分成结算独立于扣款（异步批量）：两张账本时点分离，对账面扩大；扣款成功的回合其分成无上游风险，同回合落账最简单。否决。

## Consequences

- 实现面：`deployer_earnings` 表 + 结算钩子（trySettle 成功分支旁路）+ deploy-panel 收益行，纯增量；价目表 v1 用平台统一价，per-agent 部署者定价是 v2.1 增量（价目面已在平台侧，扩展字段即可）。
- sub2api 余额成为混合余额：面板需区分「充值/消费/收益」三行（心理账户），v1 接受净额混同但必须可查明细（deployer_earnings 就是明细源）。
- 500 闸门从「静态上限」升格为「租金开关的触发器」：fleet-observer 的 agents_total 即观测点，越线告警即启用租金的运维信号。
- 部署者激励与萬星生态对齐：分成只认「外部真金回合」，内部互调（mission/委派/subsidy）不产生分成——生态收入=对外价值，内部消耗不自我膨胀。
- 本 ADR 的两个旋钮（平台抽成 30%、只抵扣不提现）是生意参数不是架构，改值不动结构；提现开放之日需新 ADR（主体/通道/税务）。
