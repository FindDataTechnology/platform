# 会话索引以 dsh 转录为事实源，SQLite 只是可重建投影

2026-10-10 事故把这条链逼到台前：小说用户 cell 的会话索引库 `app.db` 涨到 8GB（其中约 7.5GB 是 `trace_events` 原始增量载荷），cheap-3 磁盘 79% 清障时整库被删——1546 个会话、476MB 对话内容在盘上，侧边栏却空了。被删的库无法找回，但内容完好地躺在 dsh 的逐会话转录里（`dsh/sessions/<scope>/<sessionId>/session.jsonl.zstd`，含工具调用与结果），迁移时留在原地的单进程老库也意外成为 10-01 前的快照。我们从转录重建索引，并在 platform-test cell 的活库上做到 **14/14 会话逐字节一致**。

决策：**会话内容的事实源是 dsh 转录，`chat_sessions`/`chat_messages` 是它的投影**。投影可以随时从转录重建（`scripts/rebuild-chat-index.mjs`，默认 dry-run、写前备份、幂等、与实时镜像同构），因此索引库的损坏/丢失从"数据损失"降级为"一次运维动作"。推论三条：① 索引库不必也不该承载观测数据——trace 迁出为独立 `trace.db`，且载荷去冗余、定时修剪、删行回收（`bound-trace-storage`），"库被撑爆"这条路径被结构性关闭；② 重建规则必须与实时镜像同构，且该同构由对拍测试钉死（合成 fixture + 活标本 dry-run），因为两侧是复制而非共享代码；③ 转录的保留是内容保全的最后防线——任何清理动作（磁盘清障、cell 数据清扫）都不得触碰 `dsh/sessions/`。

## Considered Options

- **把索引库当事实源，定期备份**：备份是时间点快照，两次备份之间的会话仍会丢；且 8GB 级的库备份成本高、恢复窗口长。转录本就是逐会话追加的耐久日志，不另造事实源。
- **重建工具挂进启动自愈（`migrate.js`）**：重建 100+ 会话的解析不该拖慢每次启动；隐式重建还会把"索引被删"变成静默事件，掩盖真问题。显式运维动作 + dry-run 报告才是正确形态。
- **把 trace 留在同一库里、只加定时修剪**：VACUUM 需要整库重写锁，会话库大时停写窗口不可接受；单文件损坏仍会连坐。独立库让两者彻底解耦。
- **重建时保留全部原始事件（含流式 delta）**：那正是 8GB 的成因；终态正文/推理/工具证据已足够阅读与排障，delta 只对实时流有意义。

## Consequences

- 转录成为**不可清理的资产**：磁盘清障、cell 数据清扫、demo 数据回收都必须绕开 `dsh/sessions/`；任何"腾空间"动作前先确认这一点。
- 重建规则与 dsh 事件形状绑定，而上游约每日一个 rc 版本——对拍测试（活标本 dry-run）是每次重建的前置，规则漂移由它暴露，不靠记忆。
- 保真度边界是显式的：链接归一（`normalizeFunctionalRefs`）可复原，UNKNOWN_TOOL 候选附注不可复原——写进工具报告与 spec，不做静默近似。
- 子代理会话永不入索引（与实时镜像一致），其排障材料只存在于 trace 与转录两处。
