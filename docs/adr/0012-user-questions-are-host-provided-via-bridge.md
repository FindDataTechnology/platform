# 问询桥接落在宿主侧：平台补全 provider，不造反向 RPC

dsh 的 user-questions seam（ctx.userQuestions 单槽服务，standard 预设组合 ask_user_question 工具）按上游设计"拥有工具是 agent 能力、渲染是宿主 UI 能力"——TUI 自带 provider，平台此前没接，于是工具一调即 NO_PROVIDER。决策：由平台在宿主侧补全，dsh 子进程内以 bridge 插件（照 platform-permission-bridge 先例子类化 SDK server）注册 provider，ask 请求经子→宿通知（既有事件泵、独立方法、不入会话日志）转出，答案经宿→子 JSON-RPC（既有请求方向）回注并 resolve 挂起的工具调用；不引入反向 RPC（SDK client 无 onRequest，改它即改上游所有权），也不从预设移除工具（放弃 agent 交互能力，且随 dsh 预设漂移）。渲染三端：web/小程序以 ask_user_question 工具块呈现（挂起=问询卡片，完成=已答摘要，随聊天历史免费重放；服务端按 dsh 会话持有唯一 pending 态，重连/刷新随 sync 重水合，多端并发先答先得）；bot 通道（公众号/企微/飞书/telegram，机制通道无关一次全生效）以编号选项文本问出，下一条入站消息拦截为答案（数字/选项原文/自由文本=custom，不匹配重提示至多 3 次后自动取消），等待窗默认 10 分钟（env 可调）、期间 turn 硬超时暂停、到点自动取消。bot 的 answer-only 姿势对 ask 白名单豁免——问询是把决策还给用户，答案非工具衍生；子代理不得问询（DELEGATED_CALLER 护栏在 dsh 侧内建）。plan-review 专用卡片与"先讨论再答"MVP 不做（intent 忽略合法，答案编码一致）；问询不设 per-bot 开关，默认全开。
