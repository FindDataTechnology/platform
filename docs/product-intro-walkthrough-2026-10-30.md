## 坏例清单（四条真实缺陷 + 一条待复核）

### B1（阻断级）对外团队的核心闭环在 web chat 车道断：派发打不到本队
- 现象：前台调 `mcp__fleet__dispatch_post` 时填了**别的队伍**的成员 id，被「同集群」闸拒；
  走查全程 `GET /api/fleets/:id/turns` 恒为 **0**——没有任何一轮被记为本队成员回合。
- 根因：preset chat 车道**不注入 `{{fleetContext}}`**。`POST /api/fleets/dispatch` 的归因
  走 `resolveAttribution({currentPreset, ...})`（server/routes/fleets.js:920），能把 preset 归到
  本队岗位，但模型侧**拿不到本队成员 id/ref 名单**，于是按环境里能看到的旧队伍成员 id 猜。
- 附带：Q2b 里前台「没有转介接口」的说法，与 B1 同源——工具在（`mcp__fleet__dispatch_post` 已挂），
  但缺上下文时模型不会想到用。
- 影响面：不只本团队。任何「对外多岗团队 + 访客直聊前台」形态都受影响（前台拿不到队友名单＝团队退化成独角戏）。
- 修法方向：preset chat 车道为**已归属某队岗位**的 preset 注入 `{{fleetContext}}`（本队成员 ref/id
  名单 + 编导边），让派发有据可依；`dispatch` 的 `to` 支持 ref/title 解析而非只认 member id。

### B2 知识缺口：前台不知道壹座已开源
- Q3 里前台答「官方未明确标注开源协议，不方便透露」。但壹座**确已开源**（MIT，
  github.com/FindDataTechnology/platform 是公开仓），这是官网/公开仓可查的事实。
- 根因：公开的开源事实只写进了「壹座专家」persona，**前台 persona 没有这条**；前台按
  「只依据公开信息」行事时只能答「不公开」。
- 修法方向：把「壹座开源（MIT）+ 公开仓地址」补进前台知识（属公开信息，不违红线）。

### B3 内部词泄漏：来源是车道权限，不是 persona
- 现象：Q3 答「你在 facet-market（谦面市场）和 wire-ops（柏讯）操作时……」，Q5 首段 thinking
  里出现 wire-ops。`wire-ops` 是内部车道名，`facet-market` 是内部模块名。
- 根因：pack preset 聚焦时保留的 MCP 面含内部业务面——dsh-profile 日志：
  `focused on pack "壹座产品介绍（官方种子）" persona "intro-guide": keeping [facet-market,
  paper-trading, wire-ops, actions, fleet, playwright]`；同时该车道有工作区文件工具
  （glob/grep/read/bash），模型会翻本地文件再把内部词带进答案。
- 修法方向：对外团队的 preset 车道应收敛到「公开面 + fleet 桥」；工作区文件工具默认关闭
  （或限定只读公开目录）。这需要产品决策：哪些 MCP 面算公开面。

### B4 编造未公开产品面：柏讯的「需求单 / 控制台 / 24 小时响应」——**与 B3 同源（工具面），文案删净仍会复现**
- Q5 答案里出现「柏讯·需求单」「获专业实施同城异步跟进」「我们会在 24 小时内响应」「柏讯控制台」
  「市场订阅」等官网没有的产品面。官网柏讯口径只有三件：开放数据本体、MCP 数据服务、爬虫平台。
- 根因：这几句是**本仓 seed 的柏讯 persona 原文**（写 persona 时掺了内部产品面），模型照着复述——
  不是模型凭空编，是**我们自己的文案越界**。
- 修法方向：删掉未公开能力，只留官网三件 + 「官网在线体验」。
- **复测（v1.0.2 上架后）**：persona 侧已删净（发布核验 `wire persona mentions 控制台/需求单: false`），
  但复测答案**仍出现「查阅和订阅数据市场中的 A 股财务数据集」「提交数据需求单，由专业团队跟进」**——
  源头是**工具面**：`lib/board-adapters.js:323` 的柏讯「需求单」板件 + wire-ops MCP 的工具描述，
  模型照工具描述复述。故 B4 的真正修法归入 B3（对外团队的 MCP/工具面收敛），文案只是缓解。

### B5 推理痕迹经 text 信道外泄
- Q5 首段可见 `<thinking>Let me check what wire-ops tools are available…</thinking>` 原样出现在
  **text delta**（不是 thinking 事件），访客会直接看到。WeCom 车道已有
  `stripReasoningLeak()`（server/bots.js，⑨ 号真缺陷），web 文本信道未见同等剥离。
- 修法方向：web 文本输出路径复用同一剥离逻辑。

### B6 冷启动：识律专家 preset 首启慢（**已复核，降级为「慢」非「坏」**）
- 直接以 intro-lex 开聊，三次均在几十秒内返回 `Agent is still initializing`（向导 preset 正常）。
- cell 日志显示该 persona 已被 focus、`[dsh] runtime restarted for 63 catalog agent preset(s)`
  ——63 个 preset 的运行时重启期，新装 pack 的 persona 首启要等运行时就绪。
- **复核结果（走查尾声）**：识律专家最终正常应答（英文采购合同的管辖地/违约责任要点，
  结构完整、法律内容对路），只是要等运行时就绪（数十秒到数分钟）。
- 残留问题：pack persona 首启期间返回的是 **「Agent is still initializing」错误**而不是排队等待，
  对外访客是「第一句话就报错」的坏体验——同 B1 一并归平台面（4.x 接线时对外车道必然遇到）。

## 结论

- 分诊纪律（前台→识律/柏讯）与红线纪律（不泄露、不编造）在**文本层**成立且质量高；
  五线名与官网口径零错误。
- **团队形态的核心价值（前台问、专家答）在生产 web chat 车道尚未成立**，卡在 B1：
  派发上下文缺失 → 派不到本队 → 全程零队伍回合。
- 本次走查产出 4 条真实缺陷（B1/B2/B3/B4）+ 1 条待复核（B6）+ 1 条信道缺陷（B5）。
  B2/B4 是本仓文案问题（改 seed 重发即可）；B1/B3/B5/B6 属平台面，需要独立变更。
