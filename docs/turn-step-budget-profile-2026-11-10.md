# 单轮步数画像 · 哪些岗位在撞上下文墙（2026-11-10）

> 只读取证，不改代码。数据源：fd-prod 各 cell 的 `fleets.db / member_turn_events`，
> 窗口 48h。执行时生产镜像 `sha-deb4b87` 之后的 `platform-d875b887c-pkt4x`。

## 一、先划清口径（否则这张表会被误读）

| 概念 | 计数方式 | 说明 |
| --- | --- | --- |
| 「撞墙」 | `detail.steps` 是有限数字的行 | 只有被早停/溢出结算的行才带 `steps` |
| 「失败」 | `status='failed'` | 包含 503/502/timeout/其它，**不都是撞墙** |
| 样本 | 86 条带 steps 的行，散在 37 个岗位 | 单岗位样本中位数只有 1–2 条，**中位数只能当趋势** |

**两个必须记住的坑：**

1. `steps`/`lastTool` 只存在于撞墙行 —— 这是「撞墙样本」，**不是全量分布**。
2. 我 06:0x 报的「近 6h 60% 失败」是**事故窗**（04:00–06:00 上游 503 集中期），
   不是常态。48h 稳态口径下，撞墙只占 **69/761 = 9%**。两个数都对，窗口不同。

## 三、从这张表能读出的三件事

**1. 步数是唯一稳定的预测因子。** 撞墙时步数中位 ≥15 的岗位，撞墙率 17–44%；
步数中位 6 的 `巡检岗` 只有 4%（76 个回合里 44 个 ok，是这套岗位里最健康的）。
这不是「模型不好」或「岗位太笨」，是**一轮里塞的活太多**。

**2. 会话历史不是主因。** 撞墙行的 `usage_input` 实测全为 0/空（失败路径不记 tokens），
而 `政心主编` 那类岗均输入只有 7280 tok 也撞 4 次压缩 —— **压缩发生在单轮之内**
（`compactions 6–9`、`steps 11–18`），不是「会话开了太久」。
所以「换会话」不治这个病，「少做一点」才治。

**3. 少数极端值说明闸门在救场。** `监视位` 有一轮跑到 **50 步**、`合成位` 23 步、
`产出位` 24 步 —— 这类回合早停是对的，放它跑完会烧掉几倍预算且多半也做不完。

## 四、建议（口径，不是代码）

给「巡逻/汇总型」岗位定一条**每轮步数上限**，按上表分档：

| 岗位类型 | 建议上限 | 依据 |
| --- | --- | --- |
| 巡逻/巡检/监视（一步一件事） | **8 步** | `巡检岗` 中位 6 步、撞墙 4%，是现成的健康样本 |
| 撰稿/审读/优化（一轮一件产出） | **12 步** | 这几岗撞墙都在 15–25 步，砍到 12 能覆盖大多数完成态 |
| 合成/报班（多源汇总） | **15 步** | 天然需要多源，但 20–23 步明显过头 |
| CEO / 架构类（少而重） | 不设上限 | 撞墙率 5%，一轮本来就长 |

落法（任一）：

1. **prompt 侧**：在岗位说明里写「本轮最多 N 步，超出就先报数、下一轮继续」——
   最小改动，不动代码；`巡检岗` 已经天然是这个形状，可以直接抄它的措辞。
2. **运行时侧**：把 `CONTEXT_PRESSURE_COMPACTIONS` 或 turns 的 `turnTimeoutMs` 按岗位
   分级——属运行时参数，要动 `cron-runner.js`，那正是别人今天的活跃线，需协调。

**优先做 1。** 它可逆、可逐岗位灰度、不碰任何共用文件。

## 五、样本不足，这张表还不能单独下结论

- 单岗位撞墙样本中位 1–2 条，`报班岗` 10 条是唯一够看的一档；
- 48h 内 42 个岗位合计 761 回合，撞墙 69 条 —— 分母够，分子薄；
- 建议：**按小时观测那个任务**已经会报「已报数被早停 / 真失败」两半，攒满 72h
  再回头看这张表，届时 `报班岗`/`撰稿岗`/`审读岗` 三档应该有 30+ 样本。

## 六、与个人代理的关系

没有关系。撞墙行的 `detail` 里没有 `mandate` / `disclose` / `domain` 任何字段，
149 条压力失败也没有一条来自委托状或披露闸的路径。**这条线不要记在个人代理账上。**

## 七、撞墙原因一次都没判出来：`attributionFor` 从没拿到输入

这是本轮最硬的一个缺陷，属「声明 ≠ 挂载」类（本次开发里第七个同型）。

### 现象

48h 内 110 条撞墙记录，`detail.cause` **100% 是「未判定」**：

```
48h 撞墙 110 条
cause: (未判定)(110)          ← 全部没有判定
kind:  turn_budget_exceeded(86)  context_overflow(24)
model: deepseek-v4.1-flash(99)   glm-5.3-flash(11)
lastTool: (无)(28) report_status(14) bash(13) read(11) memory_handoff_begin(6) edit(5) skill(5)
均 compactions=4  均 steps=12
```

### 根因

`server/cron-runner.js:481` 的 `attributionFor({priorCacheRead, contextWindow})`
是专门为回答「历史累积还是单轮过大」写的（`rotate-cron-session-on-context-pressure 4.1`，
2026-11-09/10 两次事故的教训）。它要求两个输入都非空才出判定：

```js
if (priorCacheRead === null || priorCacheRead === undefined) return {};
if (contextWindow === null || contextWindow === undefined) return {};
```

**但全仓没有任何调用方传过这两个参数。** 实测：

```js
attributionFor({priorCacheRead: 100000, contextWindow: 128000})
// -> {"cause":"history_accumulation","priorCacheRatio":0.78}   ✅ 会判定

contextPressureDetail("turn stopped early - context pressure", {compactions: 4, reported: true})
// -> {"kind":"turn_budget_exceeded","contextPressure":true,"compactions":4,"reported":true}
//    没有 cause                                                  ❌ 生产就是这个形态
```

`attributeFailureAndSalvage`（line 518）的签名里有这两个参数、默认 `null`，
唯一调用点（line 1081）只传了 `error / compactions / reported / text /
childSessionId / mirrorSessionId / isFleet` —— **就是没传那两个。**

### 关键：数据源是有的，所以这是纯接线活

| 需要的输入 | 是否已存在 | 从哪取 |
| --- | --- | --- |
| `priorCacheRead` | ✅ 有 | `member_turn_events.usage_cached_input`（同一 session_id 的上一轮）；实测 48h 内 48% 的行有值，最大 222720 |
| `contextWindow` | 需查 | 模型配置 / catalog 里的窗口大小 |

修法（约十行，属 `cron-runner.js`）：

```js
// 在 attributeFailureAndSalvage 的唯一调用点补两个实参
const prev = db.lastTurnCacheRead?.(childSessionId);   // 上一轮的 usage_cached_input
await attributeFailureAndSalvage(ctx, {
  error: out.error, compactions: out.compactions ?? 0,
  reported: out.reported === true, text: out.text ?? "",
  priorCacheRead: prev ?? null,
  contextWindow: contextWindowFor(model) ?? null,   // 模型窗口
  childSessionId, mirrorSessionId: sessionId,
  isFleet: Boolean(fleetTagOf(job)),
});
```

### 为什么我没改

1. **这是诊断字段，不改任何回合结果**——修好只是让下一次撞墙能说清是哪种病；
2. `cron-runner.js` 今天被另一条线改了至少三轮，其中 `fix-overflow-attribution`
   改的**正是同一个特性**（溢出归因）。我去补等于两个人同时改一个函数；
3. 补 `contextWindow` 要先确认模型目录里那个字段叫什么，属跨面改动。

**结论：把这条交给 `fix-overflow-attribution` 那条线**，他们已经在动这块，
补上两个实参就通了。修好之后的判据：110 条撞墙里 `cause` 非空比例应显著 > 0，
且 `history_accumulation` 与 `single_round_too_large` 两桶都能出现。

## 八、更强的信号：prompt 里有没有写 escalate，与产出条目率差约 8 倍

前面几节都在讲「撞墙」；这一节换了问题——**为什么岗位几乎不拍板**。
起因是上产观测：6.5 小时只产出 6 条决策项（≈0.9 条/小时），
激活闸门的瓶颈不是 category（连续四次 100%），而是**事项流量本身**。

### 实测（全量，不是抽样）

按「岗位的 cadence.promptTemplate 里有没有提到 escalate / decision_queue /
拍板 / 呈报」分组，**分母用回合数**（不是岗位数——岗位数会骗人，
CEO 每小时跑、部门岗每天跑）：

| 分组 | 岗位 | 回合 | 产出条目 | **每千回合** |
| --- | --- | --- | --- | --- |
| prompt **提到** escalate | 31 | 2,313 | 237 | **102.5 条** |
| prompt **未提** escalate | 168 | 5,682 | 74 | **13.0 条** |

差 **7.9 倍**。对照组 168 个岗位 / 5,682 回合，不是从几十个里挑出来的。

### 三条必须写清的边界

1. **不是因果。** 可能 prompt 让岗位去拍板；也可能「协调者型岗位」本来就既会被
   写进 escalate 措辞、又天然产出多。分不开——要分只能做 A/B。
2. **不是必要条件。** 168 个没提 escalate 的岗位里仍有 8 个产出过条目
   （处置岗 9、agent 管家 7、巡线岗 6、法规主编 4…），说明提醒是**显著提高概率**，
   不是开关。
3. **样本集中在一个 cell**：311 条里绝大多数来自 `1da519d4`。

### 与第七节那条被撤回的假说的区别（重要）

第六节记过我撤回「步数上限 → 撞墙率」那次：那是 **5 个岗位**的对照，
扩到全量就消失了。这次：
- 分母用**回合**而不是岗位（归一化过了，差异没消失反而更清楚：17× → 7.9×）；
- 对照组是 **168 个岗位 / 5,682 回合**；
- 结论限定为「相关」，不写成「解药」。

### 值得做的一次 A/B（不是铺开）

选 3–5 个「日更 + 无 escalate 措辞 + 已有零星产出」的岗位——
`巡线岗`、`处置岗`、`发布草稿岗` 都符合（有产出说明会拍板，只是不常拍）。
在 prompt 末尾加一句，同 cell 留同节奏的对照岗，72h 后比
**每千回合产出率**是否从 ~13 抬向 ~100。

一句话措辞（可直接粘，保留 `{{fleetContext}}`）：

```
遇到需要主人拍板的事（越权、跨线依赖、需要改配置/花钱/动人）就用
decision_queue 正式呈报，写清「要拍什么 + 你的建议 + 依据」；
不要只在报数里提一句带过。收尾必 report_status。{{fleetContext}}
```

判据写死：实验组每千回合产出率 ≥ 对照组的 3 倍才算生效；< 2 倍视为无效，撤回去。

### 为什么我没改

同一件事的第三个理由了：这是**生产 prompt**，改的是别人舰队的行为边界，
而且要 owner 身份（内部桥只开 7 条 POST，成员 PATCH 不在内）。措辞与判据备好，
由你点名岗位后执行。观测任务每小时仍在跑，达标会提醒——但它不会自己开 deputy。

### 八之二、收窄到「已启用 deputy 的舰队」后，效应从 7.9× 掉到 2.8×（2026-11-10 补测）

§八 那个 7.9 倍有个未剥离的共同因子：**319 条条目里大部分来自配了 deputy 的舰队**，
而那些舰队本来就更活跃、岗位更容易被写进 escalate 措辞。把范围收到
「已 enabled 的舰队 + persona 岗」再算一次：

| 范围 | 岗位 | 回合 | 条目 | 提到 escalate | 未提 | 倍数 |
| --- | --- | --- | --- | --- | --- | --- |
| 全库 | 199 | 7,995 | 311 | 102.5 /千回合 | 13.0 /千回合 | **7.9×** |
| **仅已启用 deputy 舰队** | **7** | 1,503 | 103 | 73.4 /千回合 | 25.8 /千回合 | **2.8×** |

**结论降级：从「强信号」降为「弱信号，且样本不足」。**

三条理由，都写死在这里免得后面有人引用那个 7.9：

1. 剥掉「舰队是否启用 deputy」这个共同因子后，效应缩到 2.8 倍；
2. 收窄后只剩 **7 个岗位**，n 太小，任何倍数都不稳；
3. 按 §八 自己定的判据（实验组 ≥ 对照组 **3 倍**才算生效），**2.8 倍落在「无效」区间**。

### 因此不做 A/B

A/B 候选只有两个，且都很瘦：`助理部`（32 回合 / 3 条）、`电商部`（26 回合 / 1 条）。
在这个基数上跑 72h 说明不了任何事。

**正确的等待条件**：等「已启用 deputy 的舰队」多起来（>30 个 persona 岗 / >5,000 回合）
再回来看这条。而启用更多舰队是业务动作，不是我能推的。

### 这条线的教训（比结论本身值钱）

我在同一个问题上连续犯了两次同型错误：
- 第一次（步数上限）：拿 5 个岗位下结论 → 全量一验就没了；
- 第二次（escalate 措辞）：拿全库 199 个岗位下结论，**忘了分母里混着「配没配 deputy」这个更强的解释变量**。

两次都是**没控制混杂因子**。判据要记成一句话：
**分组前先问「这两组在别的维度上是不是本来就不一样」**——不一样就先收窄，再比。
