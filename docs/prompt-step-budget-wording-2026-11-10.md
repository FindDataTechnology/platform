# 步数上限 · 措辞草案（**假设已被证伪**，2026-11-10）

> ⚠️ **先说结论：本文原来的核心主张已被全量数据推翻。**
> 那份主张是「健康岗位与病岗位的差别就在 prompt 里的步数上限那一句」。
> 全量检验（48h、全 cell、864 回合）结果：
>
> | 分组 | 回合 | 撞墙 | 撞墙率 |
> | --- | --- | --- | --- |
> | **有**步数上限的岗位 | 117 | 10 | **9%** |
> | **无**步数上限的岗位 | 747 | 75 | **10%** |
> | 撞墙时步数中位 | 有 13 / 无 16 | | |
>
> **没有差别。** 原来那 5 个岗位的对照（巡检 4% / 报班 29% / 审读 37% / 撰稿 43%）
> 是挑出来看的，一扩到全量就消失。`巡检岗` 撞墙少，更可能是它的活本来就轻
> （一步一件事），而不是那句 prompt 的功劳。
>
> 所以下面三段措辞**不要再当成「修法」去执行**。它的正确用法只有一个：
> 当作**待验证的实验**（见 §六），或者干脆搁置。
>
> 仍然成立的部分：撞墙率稳态约 10%；78% 的压力失败其实已报过数（指标口径问题）；
> 撞墙时步数中位 13–16；绝对撞墙次数最高的是 报班岗/撰稿岗/优化岗/审读岗。

> 依据 `docs/turn-step-budget-profile-2026-11-10.md`。改 prompt 需要 owner 凭据
> （`PATCH /api/fleets/:id/members/:mid`），我没有（内部桥只开 7 条 POST 路径，
> `isInternalChild = 回环 且 不带 x-forwarded-email`），所以只能给文本。

## 一、当初为什么想抄 `巡检岗`（**已被证伪，留作记录**）

它撞墙率 4%（76 回合 / 44 ok），而它的 prompt 里有别人没有的两句：

```
步数≤5：第 4 步收尾。任一调用 >90s 无响应立即放弃落 board 记 partial，
马上 report_status——宁可窄不可超时。
```

当时的对照看起来很有说服力：有上限的 `巡检岗`(4%)、`优化岗`(17%)；没有的
`报班岗`(29%)、`审读岗`(37%)、`撰稿岗`(43%)。**但这是 5 个岗位的小样本，
扩到 864 回合后组间差异归零。** 保留这段是为了记住这个教训：小样本里的
「决定性差别」通常只是选样偏差。

## 二、三份现成措辞（追加到现有 promptTemplate 末尾，保留 `{{fleetContext}}`）

### 报班岗（撞墙 29%，步数中位 20 —— 最该改的一个）

```
周报 digest：异常台账、提案四态计数（proposed/approved/published/rejected）、成本走势；
需 Owner 拍板的事项经 decision_queue 正式呈报（decision_escalate_to_owner），禁私信替代。
步数≤10：第 8 步即收尾，未汇完的部分下一轮接着汇，不要一次汇全。任一 MCP 调用 >90s
无响应立即放弃该项并记 partial，马上 report_status——宁可少汇不可超时。
收尾必 report_status。{{fleetContext}}
```

### 审读岗（撞墙 37%，步数中位 16）

```
红线审读四清单（量级话术/内核红线/法律边界/事实纪律）：打回写明问题，放行明确标注，
逐件计入 issues_caught。每轮最多读 3 件：读完 3 件立即收尾，剩下的下一轮再读。
步数≤12：第 10 步即收尾。任一调用 >90s 无响应立即放弃该件转下一件或收尾，
report_status 记实际审读数与放弃原因——宁可少审不可超时。收尾必 report_status。{{fleetContext}}
```

### 撰稿岗（撞墙 43%，步数中位 15）

```
按选题立项成稿：量级话术口径（不用精确数字）、只写可核实功能事实。完稿交审读岗。
一轮只出一稿：写完即交审读并收尾，不要在同一轮连写多篇。步数≤12：第 10 步即收尾。
任一检索/写入调用 >90s 无响应立即放弃该段，交已写的部分——宁可短不可超时。
收尾必 report_status。{{fleetContext}}
```

### 另外三个也有撞墙记录（未读它们的原文，给通用版）

适用 `合成位`（三处，撞墙时 9/20/23 步）、`产出位`（24 步）、`监视位`（50 步）：

```
步数≤15：第 12 步即收尾，未完成部分下一轮继续。任何单次调用 >90s 无响应立即放弃
该项并记 partial，马上 report_status——宁可窄不可超时。
```

`CEO` / 架构类**不要加**：撞墙率 5%，一轮本来就该长。

## 三、怎么改（一条 PUT，改完必须回读验证）

```bash
# 1) 先读出当前 cadence（保留 cron/tz/enabled，只换 promptTemplate）
curl -s "http://<cell>/api/fleets/<fleetId>" -H 'cookie: <owner cookie>' \
  | python3 -c 'import json,sys;d=json.load(sys.stdin);[print(m["id"],m["title"],json.dumps(m["cadence"],ensure_ascii=False)) for m in d["fleet"]["members"]]'

# 2) 改一个岗位的 cadence（cadence 是对象，整块提交）
curl -s -X PATCH "http://<cell>/api/fleets/<fleetId>/members/<memberId>" \
  -H 'content-type: application/json' -H 'cookie: <owner cookie>' \
  -d '{"cadence":{"cron":"43 8 * * 1","tz":"Asia/Shanghai","enabled":true,
       "promptTemplate":"<上面那段全文>"}}'

# 3) 回读验证（关键：PATCH 可能 200 但没落库）
curl -s "http://<cell>/api/fleets/<fleetId>" -H 'cookie: <owner cookie>' \
  | grep -o '步数≤10[^"]\{0,20\}'
```

**第三步不能省。** 本仓有过「PATCH 返回 200 但字段名不对、静默无效」的先例
（`/api/cron` 的字段是 `prompt` 不是 `promptTemplate`）；舰队成员这边走的是
`cadence` 整块，形状不同，必须回读确认。

## 四、改完怎么判有效（72 小时后看同一个数）

```
撞墙率 = 该岗位 48h 内 detail.steps 为有限数字的行 / 该岗位 48h 回合数
```

判据写死：

| 岗位 | 改前 | 目标 |
| --- | --- | --- |
| 报班岗 | 29% | < 10% |
| 审读岗 | 37% | < 10% |
| 撰稿岗 | 43% | < 10% |
| 巡检岗（对照，不动） | 4% | 保持 < 8% |

若 72h 后没降，说明步数上限没被遵守——那时才轮到动运行时参数
（`CONTEXT_PRESSURE_COMPACTIONS` / `turnTimeoutMs`），那在 `cron-runner.js` 里，
是别人当天的活跃线，要协调后再动。

## 五、一个必须记住的前提

撞墙率 9% 是 48h 稳态；我 06:0x 报的 60% 是上游 503 事故窗。**别用 60% 去论证
必须改 prompt**——那会把一个局部问题说成系统性故障。

## 六、如果还想验证，只能这样做（A/B，不是全量铺开）

因为主效应没了，全量铺开等于拿生产做赌注。唯一有意义的做法：

1. 选 **2 个**绝对撞墙次数最高的岗位（当前是 `报班岗` 10 次、`撰稿岗` 9 次）；
2. 只改这 2 个的 prompt（用 §二 的措辞）；
3. 同 cell 里挑 2 个撞墙次数接近、**不改**的岗位当对照；
4. 72h 后比四组的撞墙率。若实验组显著低于对照组（比如 20% → <8%，对照仍在 15%+），
   才算有证据；否则就是无效，撤回去。

判据必须两边都测，只测实验组会重复我这次的错误。
