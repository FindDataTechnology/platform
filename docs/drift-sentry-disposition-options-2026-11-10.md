## 一、先把「死岗」这个说法纠正掉

它不是死岗，是**归档舰队里的残留**。三条实证：

| 证据 | 值 |
| --- | --- |
| 舰队 `fleet_1792956940613_vs92cg`「谦面·平台运营」状态 | **archived**（归档于 2026-10-25 20:56Z） |
| 该舰队全部回合 | 4 条，区间 `10-25 19:42Z ~ 20:17Z`，**最后一条早于归档时间 39 分钟** |
| 归档后至今（16 天）回合数 | **0** |
| 调度器判据 | `server/fleet-reconcile.js:196` —— `// Archived fleets never (re)materialize — archive is stop-and-keep.` `if (fleet.state === "archived") continue;` |

所以「再也不会跑」不是故障，是**设计如此**。真正的问题只剩一个：**同名两岗并存，台账会读出歧义**。

## 二、可删 / 不可删清单（按实测行数）

引用该成员的 3 张表、该舰队的 6 张表（实测行数）：

| 表 | 键 | 残留实例涉及行数 | 性质 | 可删？ |
| --- | --- | --- | --- | --- |
| `fleet_members` | member_id | 1 | 舰队编制 | ✅ 可删（但会留孤儿） |
| `member_reports` | member_id | 1 | 报数（append-only） | ⚠️ 删=丢历史 |
| `member_turn_events` | member_id | 1 | 回合台账（执行史） | ⚠️ 删=丢历史 |
| `fleet_runs` | root_member_id | 1 | 运行台账 | ⚠️ 删=丢历史 |
| `decision_items` | fleet_id | 5 | 拍板/决策 | ⚠️ 含 fleet 级，非本岗 |
| `fleet_row_audit` | fleet_id | 4 | **审计留痕** | ❌ **不可删** |

**两条硬事实：**
1. `deleteMember()` 只执行 `DELETE FROM fleet_members WHERE id = ?`，**不级联**（fleets-db.js:748-751）。所以删成员会留下 3 张表的孤儿行。
2. 归档舰队的成员删除接口被 409 挡住：`fleets.js:3829` —— `if (fleet.state === "archived") return res.status(409).json({ error: "This fleet is archived — its history rows are frozen" })`。**平台自身就不允许这么删。**
3. 批量 resume 也不通：`fleets.js` 里 `FLEET_BATCH_ACTIONS` 对 archived 返回 `"This fleet is archived — archived is terminal"`。

## 三、两套方案

### 方案 A：保持归档，只做「消歧」（**推荐**）

| 维度 | 内容 |
| --- | --- |
| 做什么 | 不动 DB。在台账/看板层面认「同 preset 的两个岗位里，只有 active 舰队那个在跑」；必要时在归档舰队名上加时间戳后缀以便区分 |
| 影响面 | 0 行数据变化、0 接口调用、0 出片 |
| 风险 | 极低。唯一残留：以后有人按标题搜「漂移哨」仍会看到两条 |
| 改动量 | **0 行代码**。若要做名字后缀，1 次 PATCH（但归档舰队成员编辑也被 409 挡，所以实际是 0 可做项） |
| 适用 | 认可「归档即停用」这一设计，历史留着可追溯 |

### 方案 B：彻底清理（**不推荐，且平台不支持**）

| 维度 | 内容 |
| --- | --- |
| 做什么 | 删成员行 + 清 3 张表的孤儿行；或整支归档舰队连 6 张表一起清 |
| 影响面 | 删 1 行编制 + 3 行历史（成员级）；或 3+4+2+4+5+4 = **22 行**（舰队级） |
| 风险 | ① **不可逆**，且 `fleet_row_audit` 是审计留痕，删了等于抹掉「谁在什么时候改过什么」；② 官方接口全部 409 拒绝，只能**绕过 API 直改 SQLite**，这正是本项目反复出事故的手法；③ 孤儿行会让 `listTurnEvents(memberId)` 之类按 member 聚合的读面出现「有行无岗」 |
| 改动量 | 若走官方接口：**0（不通）**。若直改 DB：1 个脚本 + 6 条 DELETE + 1 次 pod 内执行 + 回滚方案（需先 dump 22 行），≈ 半天工作量含验证 |
| 适用 | 只在你认为「归档舰队的残留污染台账」比「审计完整性」更重要时 |

### 折中（若你确实要去掉歧义）

不动 DB，只做**读面过滤**：在需要「按标题列岗位」的地方加一条 `fleet.state !== 'archived'`（多数读面**已经**这么做了——`fleets.js` 有 8 处、`fleet-events.js`、`fleet-reports.js`、`fleet-chat-context.js` 等都已过滤）。所以更可能是「你看到两条的那个面恰好没过滤」，那是**一处小改**，而不是删数据。

## 四、我的判断

**支持方案 A。** 三条理由：

1. 「停用」已经是既成事实，且是设计意图（`archive is stop-and-keep`），不需要再停一次；
2. 方案 B 要绕过 409 直改 DB，删的是**审计行**——这跟我这一整轮在做的「别让台账说谎」正好相反；
3. 如果歧义真的来自某个读面，那修那个读面（一处 `state !== 'archived'`），比删 22 行数据便宜且可逆。

**如果你看到歧义的具体位置**（哪个页面/哪个接口把两条都列出来了），告诉我，我去查那个读面有没有漏过滤——那才是根因，且改动量是「一行」。
