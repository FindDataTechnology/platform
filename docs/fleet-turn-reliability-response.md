踏勘后的两处校正，请知悉（不影响修复方向，影响你们侧的排查脚本）：

1. **"有重试逻辑但没有间隔/去重"——平台没有重试**。任务引擎一次开火=一次执行。
   同秒 3–9 行的真实机制：同舰队多个岗位的 cron 任务**同一分钟扇入触发**，在串行
   执行链上各自 0 秒 fail-fast，全落在同一秒。0 秒失败的源头不是重试风暴，是桥
   代际翻转窗（预设切换/catalog 同步/凭据 patch/崩溃重拉）打中开火点。修复方向
   与你们的建议收敛（等待+不放大），但请勿在本侧面板找退避开关——它不存在。
2. **"consecutiveFailures/errorKind……UI 无"——UI 有残血版**。岗位列表在连败 ≥3 时
   已有 `×N 连败` 徽标与 errorKind 文本，驾驶舱顶部有 failing 计数。真缺口当时在
   **状态不降级、起始时间不可得、首屏不报**——这三样 §一 上产项已补齐。

## 四、平台行为变化预告（影响你们的普查脚本）

- 回合事件 status 枚举即将增 `skipped`。请将你们的统计口径按「非 ok」全收，勿枚举

- skipped 行不携 runId/usage；连败连续判定**透明跨过** skipped（计你们口径：平台

- presence 的「最近一次执行」将只认真实回合；持续不可用超容忍窗后岗位读失联，
  reason 写明「N 轮未执行：运行时不可用」。

## 五、关联发现：滚版即全舰队停摆（与你们的爆发同族）

踏勘确认：每次网关滚版，所有 cell 被终止且注册面（内存 Map）清零，只有用户回访才
重新拉起——无人值守舰队的回合在用户回来前全部不发射。你们普查里 runtime_not_ready
爆发与滚版时段重合即此。已立案 `add-cell-lifecycle`：持久注册表+重启重建需求面+
按时刻表唤醒（不拉常驻），该 change 同时交付桌面端 cell 注册/销毁机制。
