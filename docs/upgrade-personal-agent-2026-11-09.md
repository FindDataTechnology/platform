# 升级说明 · 个人代理三层（委托状 / 事项接入 / 披露闸）

> 2026-11-09。三个能力同日归档：`agent-personal-mandate`(10 条需求)、
> `agent-personal-deputy`(7 条)、`principal-disclosure-accountability`(7 条)。
> 本文只说**升级会看到什么变化**，设计理由见各自的 design.md 与
> `docs/personal-agent-mandate-explore.md`。

## 一句话

升级**不新增任何自主权限**：未配置的域一律只给建议，未开启的来源一律不进事项。
唯一的行为变化是**可引用判例会变少**，这是有意为之。

## 一、必须知道的：可用判例会明显减少

### 现象

升级后，原来能作为 deputy 判断依据的历史裁决，**大部分不再被引用**。表现是「代理的判断理由变空/变保守」，而不是报错。

### 原因

新机制给每条记录标注来源等级，只有前两级可作判例：

| 等级 | 含义 | 可作判例 |
| --- | --- | --- |
| `owner-authored` | 主人亲手书写（含在邮件/IM 中亲自答复） | ✅ |
| `owner-approved` | 主人**原样**发出了代理的草稿 | ✅ |
| `deputy-ruled` | 代理自行裁决 | ❌ |

存量记录无法分辨「主人手打」还是「原样发了代理的稿」，因此**一律回填为 `deputy-ruled`**。

### 为什么选这个方向

判例变少只降低代理能力；判例变脏会放大错误。后者是**不可逆的信任损失**，前者只是暂时的能力缺口——补法很明确：真实使用中积累 `owner-authored`。

### 怎么补

1. **先用脚本把属于你的判断捞回来**（见下）。迁移时一刀切是过度保守的：拍板车道里
   主人的裁决本身就是他的判断，那条车道并没有「代理起草、原件发出」这种情形。
2. 正常使用即可：你亲自回复、亲自裁决的记录会自动进判例集；
3. 若某域判断明显变保守，把该域模式降到「起草，待我放行」，用你的放行积累一批 `owner-approved`；
4. 看「事项接入」分区的一致率与样本量，样本够了再谈升档。

### 迁移已按细分规则回填（2026-11-10 修订）

首次开库时的存量回填**已经**用上面这张表分批，不是一刀切。所以新部署升级后即可用，
不需要额外动作。

只有两种情况需要跑脚本：**升级早于本次修订**的部署（当时已全部记成 `deputy-ruled`），
或想先看看数字再决定。

### 回填脚本（默认只报数）

```bash
node scripts/backfill-precedent-grades.mjs --db <某 cell 的 fleets.db>            # dry-run
node scripts/backfill-precedent-grades.mjs --db <...> --apply                     # 写入
```

判据只用行里已有的列，不猜：

| 存量行的形态 | 回填为 | 理由 |
| --- | --- | --- |
| deputy 裁决 | `deputy-ruled` | 代理自裁，永不可引用 |
| 主人裁决 + **无推荐值** | `owner-authored` | 没有可照抄的推荐，只能自己判断 |
| 主人裁决 + **选择 ≠ 推荐** | `owner-authored` | 他否决了代理的倾向，这是独立判断 |
| 主人裁决 + 选择 = 推荐 | `deputy-ruled` | 分不清独立判断还是照抄，保守处理 |

不加 `--apply` 一律只读；写入前逐桶打印计数，写入后回读校验「无未分级行」。
幂等：再跑一次显示 0 变更。

**这一条仍守原方向**：分不清的不给判例资格。回填只是把**行本身能证明**的那部分还给你。

## 二、默认值即上界（升级不会放宽任何东西）

| 对象 | 升级后的默认 | 含义 |
| --- | --- | --- |
| 四个域 | 未配置 / `advise` | 只给建议，不产出可执行动作，额度为 0 |
| 三个事项来源 | 全关 | 没有任何个人事务被代理接手 |
| `ops` 域 | 沿用既有委托策略 | 舰队内部拍板行为**逐字节不变** |

`ops` 域的等价性由对照测试钉住：同一组 `(item, policy)` 在扁平旧结构与 v2 结构上跑，路由结论必须逐格相同。

## 三、需要重新认识的三个边界

### 1. 「能读」不等于「能说」

两个范围独立判定：`读取范围`（能读哪些记忆层）与 `披露范围`（能对外说哪些层）。允许读人事层，不代表允许对外提人员调整。

### 2. 类别禁令只属于 `ops` 域

`配置改动 / 人事 / 花费`三类在 `ops` 域仍然永不可委托。其余域**不按类别禁用**——不可委托的是「超过额度的动作」，不是类别本身（「花钱」在个人事务里恰恰最常被委托）。

### 3. 对外车道不提供流式

`message/stream` 在声明了 `mandateDomain` 的车道上被拒绝（`-32013`）。原因：delta 是边生成边发的，而披露裁决只对整段成立——要么毁掉流式，要么毁掉闸。**能逐段评估的东西才能流式发。**

## 四、运维需要知道的两件事

### 对外发言的原文不在平台

台账只存 `content_digest`（sha256），不存正文。**争议时需要原文，去渠道侧取**（IM/邮件那边本来就有一份）。这是刻意的：在平台再存一份「代理以你名义说过的话」，等于凭空造出第二个敏感面。

### 未配置即拒绝

`MANDATE_VERDICT_TOKEN` 未配置时，对外裁决端点返回 503，runner 侧**不发任何文本**（失败关闭），不是放行。上线前必须注入。

```bash
export MANDATE_VERDICT_TOKEN="$(openssl rand -hex 24)"
# runner 侧注入同一个值；被服务的 agent 条目上声明 mandateDomain
```

验收步骤见 `docs/disclosure-gate-verification.md`（含反证：去掉 `mandateDomain` 应恢复正常应答）。

## 三之二、新增的第五种岗位：审计官

舰队里多了一种岗位承载 `auditor`（审计官）——它替主人对代理的判断复核，出三态结论
（同意 / 有异议但放行 / 阻断并上报）。

与普通岗位的四点不同，升级后须知：

| 点 | 行为 |
| --- | --- |
| 前提 | 必须已有「授予了东西」的委托状（mode ≥ draft），否则不允许建 |
| 工具面 | 只含读与结论提交；写/发送工具在保存时即被拒 |
| 模型 | **可以**用自己的模型（与专家不同模型是设计意图，避免同向走偏） |
| 编导 | **不进工作图**：不能作为 handoff/dispatch/fanout 的两端、事件目标或裁判 |

不建审计官不影响任何既有行为；建了之后它的结论会出现在拍板队列与日报里。

## 四之二、一个已知边界：`读取范围`管不到记忆服务

`读取范围`（`read_scope`）在**本平台内**生效——读类动作的授权闸、审计官可见面、语料加载。
它**管不到** `fd-memory` 记忆服务，原因不是漏接线，而是两边判的不是同一件事：

| | 判什么 | 粒度 |
| --- | --- | --- |
| 委托状的 `读取范围` | 内容的**敏感层级**（公开/内部/机密/人事/财务） | 层级 |
| 记忆服务的 grant | **命名空间**的读写权（`r` / `rw`） | `u/<用户>`、`d/<包>`、`d/<包>/<代理>` |

记忆页面上的 `layer`（L0/L1/L2）是从行类型推出来的，不是敏感度；服务里没有
`敏感度/机密/分类` 这类字段。所以「某域不许读人事层」这句话，今天在记忆读面上
没有可对应的判定。

**实际后果**：代理若对某命名空间持 `r` 授权，就能读该命名空间下的**全部**页面——
即使其中混有人事内容，`读取范围` 也拦不住。

**当下的处置**（可以立刻做）：

1. 把高敏感内容放在**代理没有 grant 的命名空间**里（用命名空间隔离代替层级隔离）；
2. 敏感域保持 `advise`/`draft`，让代理的判断经你过目；
3. 不要把 `读取范围` 当作记忆侧的合规承诺——它在本平台内是硬闸，跨服务不是。

**要真正打通**，需要在 `fd-memory` 给页面加一个敏感度维度（与现有 layer 正交），
并在读面按它过滤。那是独立 change（跨仓），不随本次升级。

## 四之三、就绪检查（新增，只读）

```bash
node scripts/personal-agent-doctor.mjs [--db <fleets.db>] [--fleet <id>]   # 退出码 0=可用 1=有阻塞
GET /api/fleets/personal-agent/readiness                                    # 同一份结论
```

七处开关分散在三处，配错的表现都是「代理很安静」——和「没配好」一模一样。它把
「安静」拆成一条结论 + 每条的修法，并区分两类：`blocked`（这状态下它不会做任何有
价值的事，或做了不安全）与 `warn`（能跑，但你大概不是这个意思，例如判例为零 = 盲判）。

**已知边界**：这块文案是服务端中文，英文界面里会显中文——与本仓既有做法一致
（裁决摘要、拍板文本同为服务端中文），未做半套翻译。

## 五、顺带修掉的一个既有缺陷

`deserializeDecision` 的 `recommendation` 读的是 `row.resolution`——推荐值写进列却从不读回。实测两态：未决事项恒为 `null`（UI 的「推荐」那行从来没显示过），已决事项把 `resolution` 的 JSON 当推荐值打印。

已改为读自己的列。**影响面提醒**：一致率算分子的正是这个字段，修之前它读到 `null`，会把每次判断都算成不一致——所以升级后如果一致率从「接近 0」变成「有真实数字」，那是修复生效，不是统计口径变了。

## 六、回滚

| 组件 | 回滚方式 | 影响 |
| --- | --- | --- |
| 事项接入 | 删除映射即停流 | 已存在条目不受影响 |
| 委托状 | 把域改回「只给建议」 | 即时生效于后续动作 |
| 披露闸 | 不注入 `MANDATE_VERDICT_TOKEN` | 对外车道全部拒绝发出（安全方向） |
| 存储结构 | v2 blob 顶层镜像了 legacy 字段，旧读面可读 | 回滚不需迁移 |

三处新增列全部可空、只增不减；旧读面忽略它们。
