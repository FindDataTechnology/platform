# 集群平台供给开放 · paas（壹座·packs）侧需求书

> 交付对象：paas 实施者。本文是 2026-10-27 产品线方向会话的用户裁决承接单：
> 用户裁决（finddata 侧 explore，已固化于记忆 `ai-native-fleet-platform-vision-2026-10-27`）——
> ① 五线不改判；② 「集群」产品形态挂壹座；③ 内部方法论对外开放并工具化；
> ④ 供给层对外供给；⑤ 计费=按调用量（既有）+ 集群/packs 市场抽成（本单范围）。
> 本单尚无对应 OpenSpec change（paas 会话启动时自行 promote 立项，spec delta 以立项稿为准）。

---

## 1. 问题

pack/registry 生态今天**只对内部供给闭合**：

- pack 对 MCP 的引用只能通过 `registryName` 指到**我们自己的在册 server**；
- 市场 pack 的发布者被收窄在 Logto `creators` 组（我们自己的人）；
- 市场没有交易记与分成账——现有计量只到「调用量」，没有「上架物被买走」这件事。

用户裁决的方向是：客户用我们的平台构建**他们自己的**全套网络生态解决方案，供给层对外开放——
第三方（乃至客户自己）的 MCP server、工具与产能，走同一 anatomy 准入后，能被集群引用、被 pack 打包、在市场上架。

## 2. 范围

| 编号 | 交付物 | 优先级 | 说明 |
|---|---|---|---|
| A | **供应商身份类**（vendor）：registry/平台层的供应商主体，与消费者租户平行——注册、凭据轨道、配额与收益归属 | P0 | B/C 的前置；在 Logto 组 + 平台内身份之间按既有四闸先例定轨 |
| B | **供方上牌闸**：供应商的 MCP server 上牌流程（准入审查 → 工具面声明 → 商业集闸），产出物=可被 pack 以 `registryName` 引用 | P0 | 全程沿用既有-anatomy：tool-surface manifest、selfcheck、台账登记、网关注册 |
| C | **市场作者开放**：pack 铸造/发布接受供应商作者（不再限 `creators` 组），归属与署名进 manifest/条目 | P0 | 发布门规则（工具面声明闭包等）对供应商一律同轨，不降闸 |
| D | **市场交易记与分成账**：集群模板/packs 的市场购买/订阅记、分成账目与供应商结算视图 | P1 | 计费完整模型=调用量计费（既有，不动）+ 市场抽成（本交付物） |

## 3. 不在范围

- **集群主人经营面**（owner surface：KPI 报数/日报、escalate 拍板、花销视图、迭代回路）——另有需求书，主体是 paas 已有 Agent Cluster Platform 的延伸（`AGENT_CLUSTER_README.md`，pack-as-cluster/ClusterComposerModal/集群调度已在册，勿另起炉灶）。
- **L3 垂直构造器产品化**（蓝图编辑/审批闸/铸造闸/模板上架）——另有需求书，finddata 侧 spec `vertical-blueprint-constructor` 是基线。
- **多机集群运行时**——用户明确：多机运行已是既有事实，只需在 owner 面需求书里「可见」，本单不动。
- 本单不改任何**运行时契约**（pack 形状、registryName 引用、四闸语义对外保持逐字节一致）。

## 4. 验收口径

一个**非内部**供应商账号，在仅经公开入口的前提下完成全链真跑：

上牌（自有 MCP server 经供方闸进 registry）→ 铸造（含该引用的 manifest 过发布门）→ 上架（市场条目带供应商署名）→ 被客户 pack 引用安装 → 调用计量落到双方各自的账（消费侧记账、供方记收益）→ 市场分成账目正确。

每一闸的失败路径如实分类回报（准入拒/声明不全/商业集挡/署名冲突），不允许静默放行或静默失败。

## 5. 对外口径提示

市场与供给开放的对外文案按用户裁决的诚实口径写：**不说「接管人类所有工作」，说「职责变了」**——人退到集群主人/迭代者的位置。不夸张、不妥协。
